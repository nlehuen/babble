# Agentic development guidelines

This file provides guidance to [Antigravity](https://antigravity.google/), [Claude Code](https://claude.ai/code) or any other agentic development harness when working with code in this repository.

## Overview

Babble is a toy programming language running on the JVM, built as a learning project for parsing/interpreting/compiling. It uses ANTLR4 for parsing and runs either compiled to JVM bytecode with ASM (the default) or interpreted directly on the ANTLR parse tree (`-Dbabble.mode=interpret`; the interpreter is the reference implementation the compiler is tested against, and is single-threaded). Java 21 source level, JUnit 5 (Jupiter) for tests. The compiler follows `docs/design/bip001_bytecode-compiler.md` (`BIP001-I1`–`BIP001-I3`, `RM001` typed primitive lowering & static dispatch, and `RM003` JVM interfaces & proxy-free Java adapters landed in §16–§20; phase 4, ahead-of-time compilation into a jar, was done as `BIP006-I4`–`I6` in `docs/design/bip006_module-sources-and-aot.md`).

## Commands

- Build & test: `mvn package` (CI runs `mvn -B package` on JDK 21; pass `-PO2` to add a 4th `compiled-tests-O2` run at `babble.opt=2`, `babble.verify=true`). Surefire runs the suite three times by default: `default-test` (`babble.mode=interpret`, set explicitly since compile is the default), `compiled-tests` (`babble.mode=compile`, `-O1` default plus `babble.verify=true` so every generated class passes `HirVerifier` and ASM's `CheckClassAdapter`; reports in `target/surefire-reports-compiled`), and `compiled-tests-O0` (`babble.mode=compile`, `babble.opt=0`, `babble.verify=true`; reports in `target/surefire-reports-compiled-O0`), plus `compiled-tests-O2` under `-PO2` (`babble.mode=compile`, `babble.opt=2`, `babble.verify=true`; reports in `target/surefire-reports-compiled-O2`). Within each Surefire fork, JUnit Jupiter runs classes and test methods concurrently (`src/test/resources/junit-platform.properties`, `dynamic` strategy at `factor = 1.0`, sharing one warm JVM and its caches); tests that mutate process-global `System` properties or streams must be annotated with `@ResourceLock(Resources.GLOBAL)`. Test JVM heap and GC are controlled by `<surefire.jvmArgs>` (`-Xmx768m -XX:+UseParallelGC -XX:-OmitStackTraceInFastThrow` by default, the last keeping JVM exception messages stable across a warm shared JVM for the cross-mode error comparisons, also appended to JaCoCo's `argLine` in `-Pbatest`).
- Local parallel CI gate (aligned with `.github/workflows/maven.yml`): `./src/tools/ci_gate.sh` runs inside a cached `babble-ci:jdk21-node22` container (built from `src/tools/Containerfile.ci` via `podman`/`docker` for exact JDK 21 + Node 22 CI parity) by default, builds once (including Spotless check, file-size audit, and `.ba` formatter check), fans out all 8 independent CI test jobs in parallel across local CPU cores and RAM (3 Java unit-test modes, 4 JaCoCo-instrumented JVM `.batest.md` modes, and WebAssembly 3.0 parity) with bounded per-JVM JUnit threads and heap, then enforces the 6-scope `>= 80%` JaCoCo coverage and 4-way parity gate. On hosts with `<= 2` CPUs, a full CI gate automatically delegates to GitHub Actions (`gh workflow run maven.yml --ref <branch>` + `gh run watch`, requiring a clean tree pushed to `origin`). Useful flags: `--host` (bypass container and run natively on the host toolchain), `--github` (delegate to GitHub Actions from any host), `--local` (force local execution even on `<= 2` CPUs), `--no-watch`, `--fast` (skip JaCoCo), `--batest-filter <pattern>`, `--protect-batest`, `--argon`, `--skip-wasm`, `--jobs <N>`, `--threads <T>`, `--heap <MB>`.
- Run tests only: `mvn test`
- Run a single test class: `mvn test -Dtest=BabbleFunctionsTestCase`
- Run a single test method: `mvn test -Dtest=BabbleFunctionsTestCase#methodName` (runs in all three modes, or four with `-PO2`)
- Run `.batest.md` systematic tests (`BIP009`, `BIP029`): `mvn -q test [-PO2] -Dtest=BatestTestCase -Dbatest.filter=<file-or-pattern>` (fast 3- or 4-mode inner loop without JaCoCo; append `@<case-name>`, `#N`, or `:line` for a single case; pass `-Dbatest.updateIr=true` in a compiled run to bless exact `hir` golden blocks on behaviorally passing cases; partial `check` blocks require dumps `>=` `-Dbatest.minDumpSizeForUsingPartialChecks` lines, default `30`), or `mvn -q verify -Pbatest` (full 4-JVM 6-scope JaCoCo coverage report in `target/batest-report/`: `Interpreter (impl.*)`, `Compiler (-O0)`, `Optimizer (-O1)`, `Optimizer (-O2)`, `Shared Front-End (analysis)`, and `Shared Runtime (combined)`, each gated at `>= 80%` line and `>= 80%` branch coverage with 4-way behavioral parity and per-scope impact-ranked hotspots (`-Dbatest.top=10|all`, `-Dbatest.sort=score|branches|lines`); combine with `-Dbatest.filter=...` and `-Dbatest.inspect=<Class[,Class2]>` for scoped hotspot inspection, or re-run the reporter alone without re-running tests via `mvn -q exec:java@batest-report -Pbatest -Dbatest.inspect=<Class[,Class2]> -Dbatest.minLinePct=0 -Dbatest.minBranchPct=0`).
- Type checker: always on; strict static typing is the only mode (`any` / `any?`, unions `A | B`, nullables `T?`, generics with `of` syntax, `array of T`, `as`, call-site parameter inference for non-exported/non-escaping callables, required annotations on exports/escapes/interfaces/uncalled functions, full reassignment inference), and all type check failures are errors. Diagnostics go to the context's error writer (`Error : ...` with line and column), the first one fails `compile()` with `TypeCheckException`; runtime `Types.check` remains only at `as` casts and external boundaries (Java boundaries via `JavaTypes` and Java generic `TypeVariable`/`WildcardType` returns/fields, plus `InterpretedInstance`/`BabbleObjects`/`BabbleType.setMember`), with `Values.toDouble` for `int`→`double` widening (`BIP008-I5`–`I7`).
- Compiler switches (system properties): `babble.opt=0|1|2` selects optimization level (default `1` in compile mode; CLI accepts `-O0`/`-O1`/`-O2`), `babble.dumpIr=hir|hir:before|hir:canonical|hir:after:<Pass>|all|true` prints IR snapshots to stderr through `org.babblelang.ir.CliIrDumper`, `babble.dumpAxioms=<ClassOrPackage,...>` prints assumed/inferred axioms to stderr, `babble.axioms.report=true` reports curated axioms that bytecode analysis already infers as strong or stronger, `babble.dumpClasses=<dir>` writes the generated `.class` files for `javap -c -p`, `babble.trace=true` prints an ASM listing, `babble.verify=true` runs `HirVerifier` and `CheckClassAdapter`, `babble.inlineNodes=<n>` sets the largest function `-O1`/`-O2` inline (`35` HIR nodes by default, `0` disables inlining). The README's *System properties* table lists them all.
- Command line, after `mvn package` (main class `org.babblelang.Main`; the jar's manifest points at `target/lib`, filled by `maven-dependency-plugin`; `-Dbabble.mode` applies):
  - `java -jar target/babble-1.0-SNAPSHOT.jar [-O0|-O1|-O2]` starts the interactive mode; `… script.ba [arguments...]` runs a script (arguments in the `args` list; exit status 1 if it fails, 2 for a bad command line); `… -keep-alive script.ba` continues in the interactive mode after it. On a terminal the interactive mode edits lines with JLine (history in `~/.babble_history`, or `-Dbabble.history=file`; `-Dbabble.lineEditing=false` reads plain lines).
  - `… -axioms [-O0|-O1|-O2] <class-or-package>` prints what the compiler assumes (curated or inferred from bytecode) about a Java class or every public class of a package in canonical `curated.ba` syntax (exit 0, or 2 if unknown).
  - `… -crib [--host 127.0.0.1] [--port 7331] [--workers N] [--timeout 5000] [--max-requests-per-worker 200] [--no-wasm]` starts a fast, isolated loopback HTTP `.batest.md` runner (`POST /crib?<options>`, `GET /health`, `POST /recycle`, `docs/design/bip041_crib-server.md`) executing trials across `interpret`, `-O0`, `-O1`, `-O2`, and optional `wasm-O1`/`wasm-O2` inside a warm, poison-audited, killable worker JVM pool (~10–50 ms/trial) with automatic cross-mode parity diffing for `BIP032` adversarial workflows.
  - `… -dev-server [-b 127.0.0.1] [-p 8000] [-d dir] [-o none|info|verbose] [dir]` starts a lightweight static HTTP dev server over JDK 21's `SimpleFileServer` (`jdk.httpserver`, `org.babblelang.devserver`) mirroring `java -m jdk.httpserver` while accepting relative directories and guaranteeing proper MIME types for `.html`, `.js`, `.mjs`, `.wasm`, and common web assets (with `Cache-Control: no-cache`).
  - `… -compile [-O0|-O1|-O2] main.ba [-target jvm|wasm-js|wasm-bare] [-o app.jar|app.wasm] [-root dir] [-wasm-opt]` is `babblec` (ahead-of-time compilation, `docs/design/bip006_module-sources-and-aot.md` §5 and `docs/design/bip025_compile-to-wasm.md`): `-target jvm` (the default) writes a jar of the program, its static imports and a copy of the runtime, which `java -jar app.jar [arguments...]` runs on a plain JRE (exit 0, 1 if it fails to compile, 2 for a bad command line); with Babble on the class path (`java -cp app.jar:target/babble-1.0-SNAPSHOT.jar org.babblelang.runtime.Launcher …`), dynamic imports of modules the jar lacks are compiled from the program's root (`-Dbabble.root=dir`, else the index's, relative to the jar). `-target wasm-js` writes a WebAssembly 3.0 (`WasmGC`, typed funcrefs, `try_table`/`exnref`, `return_call`) `.wasm` module and a sibling Node.js/browser `.mjs` loader (`node app.mjs [arguments...]`, `wasm:js-string` glue, `axiom wasm.<mod>.<name>` host imports); `-target wasm-bare` writes a zero-import standalone `.wasm` module; `-wasm-opt` optionally post-processes the `.wasm` with Binaryen `wasm-opt -O3`.
- Formatter: `java -jar target/babble-1.0-SNAPSHOT.jar -format [-w] [-l] [-check] [file.ba | directory]...` (no file: standard input to standard output). `Main` hands what follows `-format` to `org.babblelang.Babblefmt.run`; exit status 1 for a file that can't be formatted or, with `-check`, isn't; 2 for a bad command line. Every `.ba` file of the repository must be formatter-clean: `-format -check examples src/main/java/org/babblelang/axioms` (`FormatterTestCase` and `AxiomsTestCase` fail otherwise, and `FormatterTestCase` also verifies idempotent formatting across all valid `.batest.md` snippets; `-format -w` fixes `.ba` files).
- Java formatter: `spotless-maven-plugin` with `google-java-format` (`AOSP` 4-space style, 100-char line limit) is bound to the Maven `validate` phase across `src/main/java` and `src/test/java`. Run `mvn spotless:apply` to auto-format Java sources and `mvn spotless:check` to verify.
- Benchmarks (not a test): `org.babblelang.bench.Benchmarks [filter] [interpret|O0|O1|O2...]` in the test sources, run from the repo root (`java -cp target/classes:target/test-classes:target/lib/* ...`). Its `argon` rows time a small render of `examples/raytracer` and compiling its modules; to compare two levels closely, run each in its own JVM, several times, with `-Xms1g -Xmx1g -XX:+UseParallelGC` (the modes of one run share a JVM and warm it up for each other).

The ANTLR lexer/parser/visitor classes (`org.babblelang.parser.*`) are **generated** by the `antlr4-maven-plugin` into `target/generated-sources/antlr4` from `src/main/antlr4/org/babblelang/parser/Babble.g4`. Never edit generated parser code; change the grammar and rebuild. Grammar changes require `mvn generate-sources` (or any build) before the new contexts are visible to Java code.

### Toolchains

Any JDK 21+ and Maven 3.9 build Babble; `java -version` and `mvn -v` tell what a machine has (CI and the cloud sessions run JDK 21). The build sets `release 21`, so compilation is checked against the right API level whatever the JDK, but tests execute on whichever JVM runs them.

On the maintainer's workstation, Maven and a JDK **27** come from Homebrew (`/home/linuxbrew/.linuxbrew/bin`). To reproduce CI exactly there — or to check a failure that might be JVM-version-specific — run Maven in a container, substituting any `mvn ...` command:

```
podman run --rm -v /var/home/nlehuen/babble:/work:z -v ~/.m2:/root/.m2:z -w /work \
    docker.io/library/maven:3.9-eclipse-temurin-21 mvn -B clean test
```

The image matches CI's JDK 21; mounting `~/.m2` caches dependencies between runs, and the `:z` volume flags are required for SELinux. On a machine that already runs JDK 21, plain `mvn` is CI parity.

## Conventions

- **Wording**: error messages, warnings and commit subjects put a space before a colon (`Not a number : x`, `Operator methods : a + b calls a.plus(b)`). Type diagnostics are worded like the runtime errors they predict, and both modes report the same message.
- **A new assumption goes in the axioms directory**: every built-in assumption about a Java class/method/constructor, third-party nullability annotation, optimizer `foldable`/`idempotent` method, or ordinary Babble built-in lives in `src/main/java/org/babblelang/axioms/` (`curated.ba`, `builtins.ba`, or a `*Axioms.java` stub, indexed in `src/main/java/org/babblelang/axioms/README.md`) — never hardcoded in `EffectChecker`, `JavaNullability`, `TypeChecker`, `BytecodeEffectAnalyzer`, `HirPurity`, or `OperatorTypes` (`AxiomsTestCase` enforces that `BuiltinAxioms.EMPTY` with bytecode analysis disabled knows nothing).
- **A language change** goes through every stage that sees the syntax: the grammar, the analysis passes (`BlockScopes`, `TypeChecks`, `Resolver`, `TypeChecker`), both backends (`Interpreter`, `CodeGenerator`, and `wasm` if portable), and the formatter (spacing, newlines). It comes with `.batest.md` specification tests under `src/test/batest/` (automatically checked across all 4 JVM modes, WebAssembly 3.0, pure-`SLL` parsing, and formatter idempotence — with `hir`/`wat` goldens under `compiler/` when lowering or optimization is affected), plus focused Java tests only for properties `.batest.md` cannot observe directly (e.g. `line:column` goldens in `TypeCheckerTestCase`, exact layout goldens in `FormatterTestCase`, or ASM bytecode/reflection invariants; see `src/test/AGENTS.md`).
- **Docs move with the code**: the README (its tour, and the checklists at the end: *Implemented*, *Planned*, *lessons from the ray tracer*), this file, `docs/ARCHITECTURE.md`, and the design doc of the area are updated in the same change. Use Mermaid (`mermaid` fenced code blocks) rather than ASCII art for diagrams in design docs. `examples/` is compiled by the suite (`ExamplesTestCase`) but not run; after a change that could affect them, run a ray tracer by hand (see the README; `examples/raytracer/raytracer_ppm.ba` must still render `examples/raytracer/assets/scene.ppm` byte for byte).
- **BIP feature status (`BIP###-P#` vs `BIP###-I#`)**: in BIPs and across the repository (see `docs/design/README.md`), `BIP###-P#` identifies a **planned** feature/phase and `BIP###-I#` identifies an **implemented** one. Always write full `BIP###-P#` / `BIP###-I#` identifiers (not bare `P#` shorthands). When a planned feature is fully implemented, rewrite all of its references from `BIP###-P#` to `BIP###-I#` using `python3 src/tools/mark_bip_implemented.py <PHASE...>` (supports ranges like `BIPNNN-P1..P3`, `--dry-run --diff`, and `--list-planned`).
- **Roadmap (`RM###`) references**: outside `docs/design/README.md`, only **past (implemented)** `RM###` milestones may be mentioned, with the sole exception of a PR or commit description that is directly implementing that `RM###` (e.g., mentioning `RM999` in a PR or commit description directly implementing `RM999` is fine). Never mention unimplemented `RM###` identifiers anywhere else — not in code or tests, not in other docs (`AGENTS.md`, `README.md`, `docs/ARCHITECTURE.md`, `docs/design/bip*.md` — use `BIP###` / `BIP###-P#` / `BIP###-I#` instead), and not in unrelated PR or commit descriptions — so the future part of the roadmap can be modified, merged, split, or reordered at will.
- **Commits** that fix an issue say `Fixes #N` in their message.
- **Production file-size limits (`src/main`)**: physical LOC (including comments and blanks) on `*.java`, `*.g4`, and `*.ba` under `src/main` has a **1,250-line soft limit** (signal for periodic refactoring) and a **2,000-line hard limit** enforced by `ArchitectureBoundaryTestCase` (with a shrinking `GRANDFATHERED_CEILINGS` ratchet for pre-existing oversized files). Use the [`periodic-refactor`](.agents/skills/periodic-refactor/SKILL.md) skill for weekly refactoring sessions.

## Git and pull requests

- Work on a branch, never directly on `master`. Rebase it onto `origin/master` before opening a pull request.
- **Regular commits and pushes during long sessions**: regularly commit ongoing work on your branch and push it to `origin` so no data is lost if a session crashes and your progress is externally observable. Start the commit subject with the BIP or RM being worked on, keeping the space-before-colon convention (e.g., `BIP042 : reticulating splines`). Keep intermediary commits reasonably stable (lightweight unit tests pass); save the full CI suite (`mvn package`, `-Pbatest`) for major milestones such as completing an implementation phase or finishing a session.
- Pull requests are merged as new commits (rebase or squash), so a merged branch's commits are not ancestors of `master`: start the next change from a fresh `origin/master`, not from the old branch.
- Always watch a pull request after creating it (subscribe to its activity): follow its CI and reviews and fix what fails, without asking first.

## Architecture

The pipeline is: Babble source → parsed AST → analysis (`BlockScopes` → `TypeChecks` → `Resolver` → `TypeChecker` + `EffectChecker`) → tree-walking `Interpreter` *or* unified typed `HIR` compiler (`HirBuilder` → `PassManager` (`-O0`/`-O1`/`-O2`) → `HirEmitter` → ASM JVM bytecode *or* `WasmProgramLinker` → `WasmWriter` → WebAssembly 3.0 `.wasm`), with strict separation between the parsed AST, the HIR, and the backend code.

See `docs/ARCHITECTURE.md` for the full subsystem breakdown (grammar, engine & REPL, analysis passes, modules, object model, runtime boundary & `babblec`, interpreter, HIR/optimizer/compiler, natives, WebAssembly 3.0 backend, and formatter).

## Known issues

- The interpreter cannot run a script's functions on several threads (it keeps the current scope in a field): multi-threaded `examples/raytracer/raytracer_jvm.ba` renders (`threads > 1`) only run in compiled mode (pass `threads = 1` or use `raytracer_ppm.ba` for interpreted mode).

## Tests

See [`src/test/AGENTS.md`](src/test/AGENTS.md) for the authoritative test-suite policy (`.batest.md`-first spec-driven testing, decision matrix for Java JUnit tests, suite layout map, JUnit concurrency/isolation rules, and narrow vs full verification commands) and [`src/test/batest/AGENTS.md`](src/test/batest/AGENTS.md) for `.batest.md` authoring, readability budgets, IR goldens, and the manual review checklist.

- **Primary specs (`src/test/batest/`)**: executed by `BatestTestCase` across `interpret`, `compile -O0`, `compile -O1`, and `compile -O2` (`-PO2`/`-Pbatest`) with `HirVerifier`, ASM `CheckClassAdapter`, and canonical `hir` goldens (`BIP009`/`BIP029`/`BIP039`); portable cases and `wat` goldens also run on WebAssembly 3.0 at `-O1` and `-O2` via `WasmBatestTestCase`; `ParserGrammarTestCase` verifies pure-`SLL` parsing and `FormatterTestCase` verifies idempotent formatting across all valid `.batest.md` snippets.
- **Focused Java JUnit suites (`src/test/java/`)**: reserved for properties `.batest.md` cannot observe directly — JVM bytecode/ASM/reflection/ClassLoader checks (`org.babblelang.compiler.*`, `BabbleCompilerTestCase`, `OptimizerTestCase`), `line:column` & layout goldens (`TypeCheckerTestCase`, `ResolverTestCase`, `FormatterTestCase`), CLI/AOT/REPL/filesystem/example harnesses (`MainTestCase`, `BabblefmtTestCase`, `BabblecTestCase`, `ReplTestCase`, `TerminalInputTestCase`, `FileModulesTestCase`, `ModuleSourcesTestCase`, `ExamplesTestCase`), and internal API/boundary unit tests (`org.babblelang.analysis.*`, `EGraphTestCase`, `RangeRuntimeTestCase`, `AxiomsTestCase`, `AxiomCheckerTestCase`, `BytecodeEffectAnalyzerTestCase`, `HirCanonicalPrinterTestCase`, `WasmWriterTestCase`, `ArchitectureBoundaryTestCase`, `RuntimeBoundaryTestCase`).
