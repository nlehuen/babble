# Agentic development guidelines

This file provides guidance to [Antigravity](https://antigravity.google/), [Claude Code](https://claude.ai/code) or any other agentic development harness when working with code in this repository.

## Overview

Babble is a toy programming language running on the JVM, built as a learning project for parsing/interpreting/compiling. It uses ANTLR4 for parsing and runs either compiled to JVM bytecode with ASM (the default) or interpreted directly on the ANTLR parse tree (`-Dbabble.mode=interpret`; the interpreter is the reference implementation the compiler is tested against, and is single-threaded). Java 21 source level, JUnit 5 (Jupiter) for tests. The compiler follows `docs/design/bip001_bytecode-compiler.md` (`BIP001-I1`–`BIP001-I3`, `RM001` typed primitive lowering & static dispatch, and `RM003` JVM interfaces & proxy-free Java adapters landed in §16–§20; phase 4, ahead-of-time compilation into a jar, was done as `BIP006-I4`–`I6` in `docs/design/bip006_module-sources-and-aot.md`).

## Commands

- Build & test: `mvn package` (CI runs `mvn -B package` on JDK 21). Surefire runs the suite three times: `default-test` (`babble.mode=interpret`, set explicitly since compile is the default), `compiled-tests` (`babble.mode=compile`, `-O1` default plus `babble.verify=true` so every generated class passes `HirVerifier` and ASM's `CheckClassAdapter`; reports in `target/surefire-reports-compiled`), and `compiled-tests-O0` (`babble.mode=compile`, `babble.opt=0`, `babble.verify=true`; reports in `target/surefire-reports-compiled-O0`). Within each Surefire fork, JUnit Jupiter runs classes and test methods concurrently (`src/test/resources/junit-platform.properties`, `dynamic` strategy at `factor = 1.0`, sharing one warm JVM and its caches); tests that mutate process-global `System` properties or streams must be annotated with `@ResourceLock(Resources.GLOBAL)`. Test JVM heap and GC are controlled by `<surefire.jvmArgs>` (`-Xmx768m -XX:+UseParallelGC` by default, also appended to JaCoCo's `argLine` in `-Pbatest`).
- Run tests only: `mvn test`
- Run a single test class: `mvn test -Dtest=BabbleFunctionsTestCase`
- Run a single test method: `mvn test -Dtest=BabbleFunctionsTestCase#methodName` (runs in all three modes)
- Run `.batest` systematic tests: `mvn -q test -Dtest=BatestTestCase -Dbatest.filter=<file-or-pattern>` (fast 3-mode inner loop without JaCoCo; append `#N` or `:line` for a single case), or `mvn -q verify -Pbatest` (full 3-JVM 5-scope JaCoCo coverage report in `target/batest-report/`: `Interpreter (impl.*)`, `Compiler (-O0)`, `Optimizer (-O1)`, `Shared Front-End (analysis)`, and `Shared Runtime (combined)`, each gated at `>= 75%` branch coverage with per-scope impact-ranked hotspots (`-Dbatest.top=10|all`, `-Dbatest.sort=score|branches|lines`); combine with `-Dbatest.filter=...` and `-Dbatest.inspect=<Class[,Class2]>` for scoped hotspot inspection, or re-run the reporter alone without re-running tests via `mvn -q exec:java@batest-report -Pbatest -Dbatest.inspect=<Class[,Class2]> -Dbatest.minBranchPct=0`).
- Type checker: always on; strict static typing is the only mode (`any` / `any?`, unions `A | B`, nullables `T?`, generics with `of` syntax, `array of T`, `as`, call-site parameter inference for non-exported/non-escaping callables, required annotations on exports/escapes/interfaces/uncalled functions, full reassignment inference), and all type check failures are errors. Diagnostics go to the context's error writer (`Error : ...` with line and column), the first one fails `compile()` with `TypeCheckException`; runtime `Types.check` remains only at `as` casts and external boundaries (Java boundaries via `JavaTypes` and Java generic `TypeVariable`/`WildcardType` returns/fields, plus `InterpretedInstance`/`BabbleObjects`/`BabbleType.setMember`), with `Values.toDouble` for `int`→`double` widening (`BIP008-I5`–`I7`).
- Compiler switches (system properties): `babble.opt=0|1|2` selects optimization level (default `1` in compile mode; CLI accepts `-O0`/`-O1`/`-O2`), `babble.dumpIr=hir|all|true` prints pre- and post-optimization HIR to stderr, `babble.dumpAxioms=<ClassOrPackage,...>` prints assumed/inferred axioms to stderr, `babble.axioms.report=true` reports curated axioms that bytecode analysis already infers as strong or stronger, `babble.dumpClasses=<dir>` writes the generated `.class` files for `javap -c -p`, `babble.trace=true` prints an ASM listing, `babble.verify=true` runs `HirVerifier` and `CheckClassAdapter`.
- Command line, after `mvn package` (main class `org.babblelang.Main`; the jar's manifest points at `target/lib`, filled by `maven-dependency-plugin`; `-Dbabble.mode` applies):
  - `java -jar target/babble-1.0-SNAPSHOT.jar [-O0|-O1|-O2]` starts the interactive mode; `… script.ba [arguments...]` runs a script (arguments in the `args` list; exit status 1 if it fails, 2 for a bad command line); `… -keep-alive script.ba` continues in the interactive mode after it. On a terminal the interactive mode edits lines with JLine (history in `~/.babble_history`, or `-Dbabble.history=file`; `-Dbabble.lineEditing=false` reads plain lines).
  - `… -axioms [-O0|-O1|-O2] <class-or-package>` prints what the compiler assumes (curated or inferred from bytecode) about a Java class or every public class of a package in canonical `curated.ba` syntax (exit 0, or 2 if unknown).
  - `… -compile [-O0|-O1|-O2] main.ba [-o app.jar] [-root dir]` is `babblec` (ahead-of-time compilation, `docs/design/bip006_module-sources-and-aot.md` §5): it writes a jar of the program, its static imports and a copy of the runtime, which `java -jar app.jar [arguments...]` runs on a plain JRE (exit 0, 1 if it fails to compile, 2 for a bad command line). With Babble on the class path (`java -cp app.jar:target/babble-1.0-SNAPSHOT.jar org.babblelang.runtime.Launcher …`), dynamic imports of modules the jar lacks are compiled from the program's root (`-Dbabble.root=dir`, else the index's, relative to the jar).
- Formatter: `java -jar target/babble-1.0-SNAPSHOT.jar -format [-w] [-l] [-check] [file.ba | directory]...` (no file: standard input to standard output). `Main` hands what follows `-format` to `org.babblelang.Babblefmt.run`; exit status 1 for a file that can't be formatted or, with `-check`, isn't; 2 for a bad command line. Every `.ba` file of the repository must be formatter-clean: `-format -check src/test/babble examples src/main/java/org/babblelang/axioms` (`FormatterTestCase` and `AxiomsTestCase` fail otherwise; `-format -w` fixes it).
- Benchmarks (not a test): `org.babblelang.bench.Benchmarks` in the test sources, run from the repo root.

The ANTLR lexer/parser/visitor classes (`org.babblelang.parser.*`) are **generated** by the `antlr4-maven-plugin` into `target/generated-sources/antlr4` from `src/main/antlr4/org/babblelang/parser/Babble.g4`. Never edit generated parser code; change the grammar and rebuild. Grammar changes require `mvn generate-sources` (or any build) before the new contexts are visible to Java code.

### Toolchains

Any JDK 21+ and Maven 3.9 build Babble; `java -version` and `mvn -v` tell what a machine has (CI and the cloud sessions run JDK 21). The build sets `release 21`, so compilation is checked against the right API level whatever the JDK, but tests execute on whichever JVM runs them.

On the maintainer's workstation, Maven and a JDK **27** come from Homebrew (`/home/linuxbrew/.linuxbrew/bin`). To reproduce CI exactly there — or to check a failure that might be JVM-version-specific — run Maven in a container, substituting any `mvn ...` command:

```
podman run --rm -v /var/home/nlehuen/babble:/work:z -v ~/.m2:/root/.m2:z -w /work \
    docker.io/library/maven:3.9-eclipse-temurin-21 mvn -B clean test
```

The image matches CI's JDK 21; mounting `~/.m2` caches dependencies between runs, and the `:z` volume flags are required for SELinux. On a machine that already runs JDK 21, plain `mvn` is CI parity.

## Conventions

- **Wording**: error messages, warnings and commit subjects put a space before a colon (`Not a number : x`, `Operator methods : a + b calls a.plus(b)`). Type diagnostics are worded like the runtime errors they predict, and both modes report the same message.
- **A new assumption goes in the axioms directory**: every built-in assumption about a Java class/method/constructor, third-party nullability annotation, optimizer `foldable`/`idempotent` method, or ordinary Babble built-in lives in `src/main/java/org/babblelang/axioms/` (`curated.ba`, `builtins.ba`, or a `*Axioms.java` stub, indexed in `src/main/java/org/babblelang/axioms/README.md`) — never hardcoded in `EffectChecker`, `JavaNullability`, `TypeChecker`, `BytecodeEffectAnalyzer`, `HirPurity`, or `OperatorTypes` (`AxiomsTestCase` enforces that `BuiltinAxioms.EMPTY` with bytecode analysis disabled knows nothing).
- **A language change** goes through every stage that sees the syntax: the grammar, the analysis passes (`BlockScopes`, `TypeChecks`, `Resolver`, `TypeChecker`), both backends (`Interpreter`, `CodeGenerator`), and the formatter (spacing, newlines). It comes with tests: a `.ba` script in `src/test/babble/` (run in both modes, type-checked and format-checked automatically), `DifferentialTestCase` snippets for its errors, and goldens in `TypeCheckerTestCase` / `FormatterTestCase` where they apply.
- **Docs move with the code**: the README (its tour, and the checklists at the end: *Implemented*, *Planned*, *lessons from the ray tracer*), this file, `docs/ARCHITECTURE.md`, and the design doc of the area are updated in the same change. Use Mermaid (`mermaid` fenced code blocks) rather than ASCII art for diagrams in design docs. `examples/` is compiled by the suite (`ExamplesTestCase`) but not run; after a change that could affect them, run a ray tracer by hand (see the README; argon must still render `examples/raytracer-argon/scene.ppm` byte for byte).
- **BIP feature status (`BIP###-P#` vs `BIP###-I#`)**: in BIPs and across the repository (see `docs/design/README.md`), `BIP###-P#` identifies a **planned** feature/phase and `BIP###-I#` identifies an **implemented** one. Always write full `BIP###-P#` / `BIP###-I#` identifiers (not bare `P#` shorthands). When a planned feature is fully implemented, rewrite all of its references from `BIP###-P#` to `BIP###-I#` using `python3 src/tools/mark_bip_implemented.py <PHASE...>` (supports ranges like `BIPNNN-P1..P3`, `--dry-run --diff`, and `--list-planned`).
- **Roadmap (`RM###`) references**: outside `docs/design/README.md`, only **past (implemented)** `RM###` milestones may be mentioned, with the sole exception of a PR or commit description that is directly implementing that `RM###` (e.g., mentioning `RM999` in a PR or commit description directly implementing `RM999` is fine). Never mention unimplemented `RM###` identifiers anywhere else — not in code or tests, not in other docs (`AGENTS.md`, `README.md`, `docs/ARCHITECTURE.md`, `docs/design/bip*.md` — use `BIP###` / `BIP###-P#` / `BIP###-I#` instead), and not in unrelated PR or commit descriptions — so the future part of the roadmap can be modified, merged, split, or reordered at will.
- **Commits** that fix an issue say `Fixes #N` in their message.

## Git and pull requests

- Work on a branch, never directly on `master`. Rebase it onto `origin/master` before opening a pull request.
- **Regular commits and pushes during long sessions**: regularly commit ongoing work on your branch and push it to `origin` so no data is lost if a session crashes and your progress is externally observable. Start the commit subject with the BIP or RM being worked on, keeping the space-before-colon convention (e.g., `BIP042 : reticulating splines`). Keep intermediary commits reasonably stable (lightweight unit tests pass); save the full CI suite (`mvn package`, `-Pbatest`) for major milestones such as completing an implementation phase or finishing a session.
- Pull requests are merged as new commits (rebase or squash), so a merged branch's commits are not ancestors of `master`: start the next change from a fresh `origin/master`, not from the old branch.
- Always watch a pull request after creating it (subscribe to its activity): follow its CI and reviews and fix what fails, without asking first.

## Babble Improvement Proposals (BIPs) and Roadmap

Design documents live in `docs/design/` as numbered BIPs; see `docs/design/README.md` for the authoritative index of all implemented and planned BIPs (`BIP001` onward), their statuses, and the milestone roadmap.

## Architecture

The pipeline is: Babble source → ANTLR4 parse tree → analysis (`BlockScopes` → `TypeChecks` → `Resolver` → `TypeChecker` + `EffectChecker`) → tree-walking `Interpreter` *or* ANTLR-free `HIR` compiler (`HirBuilder` → `PassManager` → `HirEmitter` → ASM JVM bytecode).

See `docs/ARCHITECTURE.md` for the full subsystem breakdown (grammar, engine & REPL, analysis passes, modules, object model, runtime boundary & `babblec`, interpreter, HIR/optimizer/compiler, natives, and formatter).

## Known issues

- The interpreter cannot run a script's functions on several threads (it keeps the current scope in a field): the fable ray tracer, which renders on 16 threads, only runs in compiled mode.

## Tests

Tests live in `src/test/java/org/babblelang/tests`. Most extend `BabbleTestBase`, which offers `interpret(String)` for inline snippets and `interpretFile(String path)` for `.ba` scripts. End-to-end language tests are `.ba` files in `src/test/babble/` (referenced by relative path, so tests must run from the repo root, as Maven does). In-language `assert(...)` calls are the assertion mechanism inside `.ba` scripts.

- All three modes (`interpret`, `compile -O1`, `compile -O0`): `DifferentialTestCase` runs every `.ba` file and a list of snippets in all three modes and compares results, output and errors; `BatestTestCase` (`org.babblelang.tests.batest`) runs every `.batest` file under `src/test/batest/` (`{{{{{`/`}}}}}` cases, `==========` virtual modules, `----------` session inputs) with leak-free error normalization (`BIP009`; an expected line starting with `~~ ` is a regular expression, for JDK-version-specific wording), backed by `-Pbatest` 3-JVM 5-scope JaCoCo reporting (`BatestCoverageReporter`). See `src/test/batest/AGENTS.md` for `.batest` authoring and review guidelines (size budgets, silent `assert(...)` cases, preambles/helpers/rigs, and manual verification checklist).
- Modules: `BabbleModulesTestCase` covers modules, in a `MapModuleSource`; `FileModulesTestCase` what is particular to files (real paths, symbolic links, absolute paths), rooted file sources and class path modules; `ModuleSourcesTestCase` the `ModuleSource` contract (an in-memory source that records what it is asked); and `src/test/babble/Modules.ba` with the fixtures in `src/test/babble/modules/`.
- Object model: `BabbleObjectModelTestCase` and `BabbleJavaObjectsTestCase` (§10 of its design doc).
- Compiler, optimizer and analysis: `BabbleCompilerTestCase` covers compiled-mode specifics (method names, generated classes, stack-trace lines, class verification, method/constant splitting); `OptimizerTestCase` covers `BIP014-I2` / `BIP027-I2` HIR passes (unified E-graph constant folding & strict IEEE-754 algebraic/`idempotent` simplification, intra-module & `babblec` AOT cross-module inlining, error line fidelity, DCE including `@TERMINATING`-gated pure loops/calls, structured LICM, `dumpIr`, and 3-way parity); `EGraphTestCase` covers `org.babblelang.ir.egraph`; `ResolverTestCase` has golden tests of name bindings; `TypeCheckerTestCase` has golden tests of type diagnostics (`line:column message`) and checks every `.ba` script checks cleanly; `EffectsTestCase`, `AlgebraicAndTerminationTestCase`, and `src/test/babble/Effects.ba` cover `RM002` (`BIP007-I1`) & `RM012` (`BIP027-I3`–`I6`) effect/algebraic inference, E-graph algebraic & partial-derivative sign verification, polynomial SCP termination, `mut`/`borrow` alias & exclusivity rules, higher-order specialization, and Java `axiom`/`@Pure` boundaries; `ArchitectureBoundaryTestCase` enforces import isolation (ANTLR-free cores, no `engine.impl` back-refs) and LOC ceilings (`BIP027-D9`); `RuntimeBoundaryTestCase` keeps the runtime free of the front end (`parser`, `analysis`, `ir`, `opt`, `compiler`, `interpreter`, `engine`).
- Sessions: `ReplTestCase` covers sessions (shadowing, static checks and types across inputs, modules loaded once per session), `classify`, and the loop's transcripts.
- Formatter: `FormatterTestCase` has golden tests of the formatter and checks every `.ba` script of the repository formats to a fixed point; `org.babblelang.BabblefmtTestCase` covers its command line.
- Examples: `ExamplesTestCase` compiles every script of `examples/` without running it (the ray tracers take minutes to run): with `compileProgram` and its static imports in the compiled run, through `compile()` (parse, analysis, type checking) in the interpreted one.
- Command line and babblec: `org.babblelang.MainTestCase` covers the command line (scripts, arguments, `-O0`/`-O1`/`-O2`, `-keep-alive`, `-compile`, exit statuses); `BabblecTestCase` compiles programs into jars and runs them in fresh JVMs with the jar alone (output, arguments, errors, dynamic imports, contents, byte-identical rebuilds), and with Babble on the class path (`runWithBabble`: modules compiled while running, the root).
