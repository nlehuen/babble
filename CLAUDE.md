# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Babble is a toy programming language running on the JVM, built as a learning project for parsing/interpreting/compiling. It uses ANTLR4 for parsing and runs either compiled to JVM bytecode with ASM (the default) or interpreted directly on the ANTLR parse tree (`-Dbabble.mode=interpret`; the interpreter is the reference implementation the compiler is tested against, and is single-threaded). Java 21 source level, JUnit 5 (Jupiter) for tests. The compiler follows `docs/design/bytecode-compiler.md` (phases 1 to 3 done; §16 to §18 there list what landed; phase 4, ahead-of-time compilation into a jar, was done as M5 of `docs/design/module-sources-and-aot.md`).

## Commands

- Build & test: `mvn package` (CI runs `mvn -B package` on JDK 21). Surefire runs the suite twice: `default-test` (`babble.mode=interpret`, set explicitly since compile is the default) and `compiled-tests` (`babble.mode=compile`, plus `babble.verify=true` so every generated class passes ASM's `CheckClassAdapter`; reports in `target/surefire-reports-compiled`).
- Run tests only: `mvn test` (`mvn test -DargLine="-Dbabble.typing=strict"` for strict typing mode)
- Run a single test class: `mvn test -Dtest=BabbleFunctionsTestCase`
- Run a single test method: `mvn test -Dtest=BabbleFunctionsTestCase#methodName` (runs in both modes)
- Type checker: always on; all type check failures are errors. Diagnostics go to the context's error writer (`Error : ...` with line and column), the first one fails `compile()` with `TypeCheckException`, and declared types are checked at runtime (T9). `babble.typing=strict` enables strict typing (`any`, `as`, required parameter annotations, full reassignment inference).
- Compiler debugging switches (system properties): `babble.dumpClasses=<dir>` writes the generated `.class` files for `javap -c -p`, `babble.trace=true` prints an ASM listing, `babble.verify=true` runs `CheckClassAdapter`.
- Command line, after `mvn package` (main class `org.babblelang.Main`; the jar's manifest points at `target/lib`, filled by `maven-dependency-plugin`; `-Dbabble.mode` applies):
  - `java -jar target/babble-1.0-SNAPSHOT.jar` starts the interactive mode; `… script.ba [arguments...]` runs a script (arguments in the `args` list; exit status 1 if it fails, 2 for a bad command line); `… -keep-alive script.ba` continues in the interactive mode after it.
  - `… -compile main.ba [-o app.jar] [-root dir]` is `babblec` (ahead-of-time compilation, `docs/design/module-sources-and-aot.md` §5): it writes a jar of the program, its static imports and a copy of the runtime, which `java -jar app.jar [arguments...]` runs on a plain JRE (exit 0, 1 if it fails to compile, 2 for a bad command line). With Babble on the class path (`java -cp app.jar:target/babble-1.0-SNAPSHOT.jar org.babblelang.runtime.Launcher …`), dynamic imports of modules the jar lacks are compiled from the program's root (`-Dbabble.root=dir`, else the index's, relative to the jar).
- Formatter: `java -jar target/babble-1.0-SNAPSHOT.jar -format [-w] [-l] [-check] [file.ba | directory]...` (no file: standard input to standard output). `Main` hands what follows `-format` to `org.babblelang.Babblefmt.run`; exit status 1 for a file that can't be formatted or, with `-check`, isn't; 2 for a bad command line. Every `.ba` file of the repository must be formatter-clean: `-format -check src/test/babble examples` (`FormatterTestCase` fails otherwise; `-format -w` fixes it).
- Benchmarks (not a test): `org.babblelang.bench.Benchmarks` in the test sources, run from the repo root.

The ANTLR lexer/parser/visitor classes (`org.babblelang.parser.*`) are **generated** by the `antlr4-maven-plugin` into `target/generated-sources/antlr4` from `src/main/antlr4/org/babblelang/parser/Babble.g4`. Never edit generated parser code; change the grammar and rebuild. Grammar changes require `mvn generate-sources` (or any build) before the new contexts are visible to Java code.

## Conventions

- **Wording**: error messages, warnings and commit subjects put a space before a colon (`Not a number : x`, `Operator methods : a + b calls a.plus(b)`). Type diagnostics are worded like the runtime errors they predict, and both modes report the same message.
- **A language change** goes through every stage that sees the syntax: the grammar, the analysis passes (`BlockScopes`, `TypeChecks`, `Resolver`, `TypeChecker`), both backends (`Interpreter`, `CodeGenerator`), and the formatter (spacing, newlines). It comes with tests: a `.ba` script in `src/test/babble/` (run in both modes, type-checked and format-checked automatically), `DifferentialTestCase` snippets for its errors, and goldens in `TypeCheckerTestCase` / `FormatterTestCase` where they apply.
- **Docs move with the code**: the README (its tour, and the checklists at the end: *Implemented*, *Planned*, *lessons from the ray tracer*), this file, and the design doc of the area are updated in the same change. `examples/` is compiled by the suite (`ExamplesTestCase`) but not run; after a change that could affect them, run a ray tracer by hand (see the README; argon must still render `examples/raytracer-argon/scene.ppm` byte for byte).
- **Commits** that fix an issue say `Fixes #N` in their message.

## Git and pull requests

- Work on a branch, never directly on `master`. Rebase it onto `origin/master` before opening a pull request.
- Pull requests are merged as new commits (rebase or squash), so a merged branch's commits are not ancestors of `master`: start the next change from a fresh `origin/master`, not from the old branch.

## Architecture

The pipeline is: Babble source → ANTLR4 parse tree → analysis → tree-walking interpreter *or* bytecode compiler. There is no separate AST; both backends work on ANTLR `ParserRuleContext` nodes directly.

- **Grammar** (`src/main/antlr4/.../Babble.g4`): ~100 lines defining the whole language. Everything is an `expression` (no statements); labeled alternatives (`# defExpression`, `# call`, etc.) become the visitor methods. Visitor generation is on, listener off.
  - Newlines are significant: `NL` tokens (with `;`) separate statements, and `NL*` is permitted only after continuation tokens (binary operators, `,`, `=` and the compound `+=`/`-=`/`*=`/`/=`, `->`, `then`, `else`) and before a selector's `.` (a line may start with `.`; `.5` lexes as a number).
  - Never between an expression and a following `(`, which would recreate the call/juxtaposition ambiguity, nor before a unary `-` (`# negate`, binding tighter than binary operators; a negated integer literal is folded, so `-2147483648` is an int), so `a` then `-b` on the next line are two expressions.
  - `else if` is a second `# ifExpression` alternative ending with `elseIf=expression` (a predicate requires `if` next): ending the alternative makes ANTLR parse it at the `if`'s precedence, so `… else (c) + 1` applies to the whole chain.
- **Engine entry point** (`org.babblelang.engine`): JSR-223 (`javax.script`) implementation. `BabbleScriptEngineFactory.INSTANCE` → `BabbleScriptEngine` (lexes/parses, runs the analysis, `Compilable`). `getMode()` picks `COMPILE` (`compiler.CompiledBabbleScript`, the default) or `INTERPRET` (`BabbleCompiledScript`) from the `babble.mode` engine attribute or system property.
  - The built-in "implicits" (`print`/`println`, `assert`, `import`, `same`, `classof`, the number conversions `int`/`double`, and the `java`/`javax` root packages; French aliases `affiche`/`afficherc`, `suppose`, `importe`) come from `runtime.Implicits.create()`.
  - `createRuntime(ScriptContext)` builds each eval's namespaces: implicits → `STDOUT` (`Implicits.withOutput`, the context writer) → script root (ENGINE_SCOPE bindings + top-level defs), and its `Modules` (the engine's `EvalModules`: the eval's loaded modules, compiled through the module cache).
- **Sessions and the REPL** (`docs/design/repl.md`): `BabbleSession` (`engine.newSession(context)`) evaluates successive inputs that see each other's definitions.
  - Each input that defines names or packages is a scope *nested* in the previous one, in the analysis (`AnalysisSession`: chained file `ScopeNode`s, plus the type nodes, definition/occurrence scopes and reassigned defs the passes look up; `BlockScopes.analyze(file, session)` then `session.commit(analysis)`) and at runtime (a child `Namespace`; scripts run in a given namespace through `BabbleScript.eval(ScriptRuntime)`, the base class of both script kinds). So a redefinition shadows, earlier code keeps its definitions, and nothing static is weakened.
  - The session keeps one `Modules` for its lifetime, so a module imported by several inputs is loaded once. `BabbleSession.classify` tells `EMPTY`/`INCOMPLETE`/`COMPLETE` inputs apart from where the parser fails (`ParseFailure.atEnd`).
  - `org.babblelang.Repl` is the loop on top: prompts, multi-line input, `:help`/`:cancel`/`:quit`, values shown (strings quoted), errors printed without ending the loop. `org.babblelang.Main` is the command line: it runs a script as the first input of a session (`BabbleSession.eval(source, sourceName)`), binds `args` (`JavaObject.of(list)`), and starts the loop when there is no script or with `-keep-alive`.
  - Parsing is shared with `compile()` (`BabbleScriptEngine.parse`), which reports `Syntax error : unexpected …` with line and column; type diagnostics throw `TypeCheckException`.
- **Analysis** (`org.babblelang.analysis`): runs in both modes at `compile()` time, in four passes, in this order (`BlockScopes.analyze`):
  1. `BlockScopes` computes each scope's `def`s for hoisting and the members of classes, objects and interfaces (`TypeNode`), and checks placement (`return`, `this`, `super`, `private`, header `def`s, value-class rules).
  2. `TypeChecks` resolves `implements`/`extends` statically (interface literals or Java interfaces), checks completeness, default conflicts, Java arities and `super`, and reports private/read-only access when the receiver's class is statically known.
  3. `Resolver` (result: `ScopeAnalysis.resolution()`) binds every name to a frame `Variable` or to a runtime lookup; only the compiler uses it.
  4. `TypeChecker` (`docs/design/type-system.md`) runs gradual typing over `Type` (`dynamic`, `int`/`double`/`bool`/`string`, `null`, function types with named/optional parameters, nominal class/interface instance types, class values, packages, Java classes and instances), inference for never-reassigned unannotated defs, and diagnostics (`ScopeAnalysis.typeDiagnostics()`) worded like the runtime errors they predict.
  - Runtime checks: `TypeChecker` records, per boundary (parameter declarations, function literals' results, annotated defs, unqualified assignments), a `Types` descriptor (`ScopeAnalysis.checkedType(ctx)`), and the declared types of members and statics go into the `ClassShape` (with an id per class/interface expression, for nominal checks: in a module, its key and the type's name, `lib/vec3.ba#Vec3`, stable across compilations; elsewhere JVM-unique, `T17`). Both backends call `runtime.Types.check` at those points; `BabbleInstance`/`BabbleType.setMember` check member and static writes.
  - Results live in `ScopeAnalysis` (declared names, `ClassShape`s, def targets, super targets, warnings with line and optional column, type diagnostics). Non-typecheck warnings go to the context's error writer as `Warning : ...`, type diagnostics as `Error : ...`; errors become `ScriptException`s worded like runtime ones.
- **Modules** (`docs/design/modules.md`): `export def x = …` / `export package p ( … )` (top level of a file only, checked by `BlockScopes`; names in `ScopeAnalysis.exports()`) and `import("path.ba")`.
  - Loading: `ImportFunction` sends names ending in `.ba` to `BabbleScriptEngine.importModule`, which goes through the runtime's `Modules` to the engine's `EvalModules.load`. The engine's `ModuleSource` (*M4*, `docs/design/module-sources-and-aot.md` §4; the `babble.moduleSource` attribute, default `FileModuleSource.INSTANCE`; also `FileModuleSource.rooted(dir)`, `MapModuleSource`, `ClassPathModuleSource`, sharing `LogicalPaths` for `/`-separated paths) resolves the name from the importing module (a `ModuleId`: key + display name; the importer's source name maps back to it through `compiledAs`, else `ModuleSource.identify`, which for files accepts a `FILENAME` that does not exist).
  - Running: the module is compiled in the engine's mode and run once per eval on a `ScriptRuntime` of its own (own root namespace, same context and bindings, the eval's loaded modules keyed by `ModuleId.key`). The result is a `runtime.Module`: a read-only `HasMembers` view of the exported names of that root, registered before the file runs so that cycles work. No backend has module-specific code: both script classes extend `BabbleScript` (`eval(ScriptRuntime)`, `exports()`).
  - *Static imports* (M2): pass 1 records each `import("….ba")` call with a string literal (`BlockScopes.imports`); after pass 1, `BlockScopes.analyze(…, ModuleLoader)` hands the file's `ModuleInterface` (exported names) to the loader (`started`, for cycles), then loads each import's interface (`load`; the engine's `Loader`, relative to the importing file), and `TypeChecks` resolves `implements`/`extends`/`super(I)` paths through modules (`resolveDefinition`, `moduleOf`, the exporter's `resolveExport`) and reports `No such export` / `Cannot assign to an export` (errors).
  - The module cache (`compiledModule`, under `moduleLock`) keys by `ModuleId.key` and keeps a module's compiled script and interface while the source, the mode and the version (`ModuleSource.version`; a content hash for files) of every module its analysis read are unchanged; runtime `import` goes through it too.
  - *Types across modules* (M3): a static import's type is `Type.Module`, whose members are the exporter's types; the `ModuleInterface` carries the exporter's `TypeChecker` once it ran (`typed`), and a checker asks the owning file's checker (`ask`, through `owners`, synchronized on it) for anything defined in another file: declarations, members, constructor parameters, expressions. Annotations naming a class through a module (`shapes.Circle`, or an alias of it) are nominal `Instance` types (`typeThroughModule`). Files in an import cycle are `dynamic` to those analysed before them.
- **Block scope**: the file, function literals (parameters + body top level), packages, and every other block (block expression, `if` branch, `while` body — fresh per iteration) are scopes. Names a scope defines are declared (unset) on entry; reading or assigning them before their `def` runs fails with `Name used before definition`. Blocks that define nothing get no namespace. Top-level `def`s of class, object, interface and static bodies declare *members*, which bind no unqualified name.
- **Object model** (`docs/design/object-model.md`): `class (params) implements I ( body ) static ( … )`, `value class`, `interface extends … ( … )`, `object implements … ( … )`, `this`, `super.m()`/`super(I).m()`, `x is T`, `private`, and the natives `same`/`classof`. Members are reached only as `this.x` or `obj.x`; `this.x` goes through `Members.selectOwn`/`assignOwn`, the only path that may see private members.
  - *Operator methods*: when the left operand of `+ - * /`, or the operand of unary `-`, is a `BabbleInstance`, the operator calls its public `plus`/`minus`/`times`/`div`/`neg` (`Operators.method`, `Operators.NEGATE`; missing: `No such member : plus`). The interpreter does it in `visitBinaryOp`/`visitNegate` (`operatorCall`); compiled code evaluates both operands into locals, then branches on `instanceof BabbleInstance` to the same select and call `invokedynamic` sites `a.plus(b)` compiles to (`operatorCall`), so it is as fast; both use `Interpreter.operatorSite` for the call's messages. The type checker types it as that call when the left type is an `Instance`, and no longer requires numbers on the right of `- * /` when the left is `dynamic`.
  - *Compound assignment* (`x op= v`, the `op` token of `# assignExpression`, `Operators.compound`) is `x = x op v` with the target read before `v` and an `obj.x` receiver evaluated once: the interpreter's `compound`, the compiler's `compoundAssignment` (sharing `arithmetic` with `visitBinaryOp`), and the type checker's `compoundAssignment` (sharing `binaryOp`); the left operand's text in messages is `Interpreter.targetText` (`x`, `obj.x`).
  - Runtime: `BabbleClass` (callable class value, statics, inherited defaults), `BabbleInstance` (member array, value-class equality/hash/`toString`), `BabbleInterface`, `ClassShape` (static description, string-encoded for compiled code), `Classes` (helpers both backends call), `Supers`. Java boundary: `Values.toJava`/`fromJava`, `Faces` (proxies for instances implementing Java interfaces and for functions converted to functional interfaces), `Overloads`/`JavaTypes`.
- **Runtime boundary** (`docs/design/module-sources-and-aot.md` §3): what a compiled program needs to run is `org.babblelang.runtime` and the built-ins of `engine.impl.natives` and `engine.impl.natives.java`.
  - `BabbleException` is in `runtime` too, so error messages start with `org.babblelang.runtime.BabbleException:`. The boundary references nothing of the front end (parser, analysis, compiler, interpreter, engine), no third-party library and no JDK module but `java.base`; `RuntimeBoundaryTestCase` enforces it by reading the class files' constant pools. `mvn package` also builds it alone as `babble-<version>-runtime.jar` (classifier `runtime`).
  - `import` reaches modules through the runtime interface `Modules` (`load(name, importerSourceName, rt)`), which the engine implements; `ScriptRuntime` is `(root, writer, modules)`, with no `javax.script`.
  - *babblec* (M5b): `compiler.Babblec.compile(main, root, jar, context)` compiles through `BabbleScriptEngine.compileProgram(source, mainName)` (a `FileModuleSource.rooted(root)`, compile mode; the main module and every module its analysis read, as `ProgramModule`s) and writes a reproducible jar (sorted entries, fixed time stamps): the generated classes, the index `babble/modules.index` (`runtime.ProgramIndex`: main key, the root relative to the jar's directory; per module key, display name, class, exports), the runtime classes copied from wherever `Launcher` was loaded, and `Main-Class: org.babblelang.runtime.Launcher`.
  - The launcher runs the main class's `run(ScriptRuntime, Namespace)` with `args` bound and a `Modules` over the index, resolving import names from the importer's key with `runtime.LogicalPaths`; a module not in the index goes to a `runtime.ModuleCompiler` found through `ServiceLoader` (M5c: the full jar registers `compiler.FileModuleCompiler` in `src/main/resources/META-INF/services`, an engine per root compiling through `compileProgram`; the program's own modules stay the jar's at runtime), and without one fails with `a compiled program only has the modules it imports statically`.
- **Runtime** (`org.babblelang.runtime`, no ANTLR dependency): everything both backends call — `Operators`, `Truth`, `Members`, `Arguments` (the one implementation of argument binding), `Calls`, the `Callable` calling convention `call(ScriptRuntime, Object[] args, String[] names, CallSite)`, `BabbleFunction`/`BoundMethod`, `CompiledFunction`/`FunctionBody`, `CallSite`/`OpSite` (source texts for error messages), `ScriptRuntime` (per-eval root namespace, output writer, `Modules`), and the scopes `Namespace`/`Scope`/`Slot`.
- **Interpreter** (`org.babblelang.engine.impl.Interpreter`): extends the generated `BabbleBaseVisitor<Object>`; one `visitX` method per grammar alternative. It tracks the `last` visited context so `BabbleCompiledScript` can report the line number on error. `return` is a `ReturnException` caught by `Function.invoke`. Class constructors are `InterpretedClassBody`.
- **Compiler** (`org.babblelang.compiler`, `docs/design/bytecode-compiler.md`): `CodeGenerator` emits a script class (a module's is named after its key, `BabbleCompiler.className`: `lib/vec3.ba` → `babble/lib/vec3$ba`, the same every compilation; other scripts get `org/babblelang/generated/Script$N`).
  - Its methods: `run(ScriptRuntime, Namespace)` (split into `run$k` when large); one `fn$N$name` static method per function literal, taking its arguments spread (`(self, thiz, rt, binder, p0, …)`, its *direct entry point*), plus an `fn$N$name$call` adapter taking them as an array (wrapped as `FunctionBody` via `LambdaMetafactory`; functions with more than 200 parameters only have the array form); one `cls$N$Name` constructor per class/object expression (wrapped as `ClassBody`); and static constant fields built in `<clinit>` helpers.
  - Phase 2: function, block, class-body and static-block variables are JVM locals, or `Cell`s when captured (function and class values carry their captured cells); the file, packages, interface bodies and any scope declaring a `package` keep phase 1 namespaces. Each class/object expression whose body keeps no namespace also gets its own JVM class `Script$N$k$Name extends BabbleInstance` (a field per member, methods as instance methods behind shared `CompiledMethod`s, hidden `$v$x` fields for constructor cells methods capture); `this.x`/`this.m()` compile to `GETFIELD`/`PUTFIELD`/`INVOKEVIRTUAL` (of the direct entry point when the call is positional).
  - Phase 3: other calls and `obj.x` selections are `invokedynamic` sites bootstrapped by `runtime.Bootstrap`, each with an inline cache of up to 4 guarded fast paths before going generic: a `CompiledFunction`/`CompiledMethod`'s direct handle; a callee class's own `call`; a compiled class's field getter, looked up with private access to that class so that it works on classes other scripts compiled, in their own class loaders; a constant Java package/class member; a Java object's method bound to receivers of its class; and for a call to a Java method with positional arguments, `JavaLinker.call` (a guard on the `JavaMethod` and the arguments' kinds and the resolved method's `MethodHandle`, converting as `Values.toJava`/`fromJava` and failing as reflection does; no fast path for Babble instance, class or function arguments). Java overload resolution is cached per argument kinds (`Overloads.Cache`, both modes), and its candidates (`JavaTypes.methods`) skip bridge methods except visibility bridges (`StringBuilder.length()`).
  - Invariants: every expression leaves exactly one `Object` on the stack, and the operand stack is empty at loop heads (HotSpot OSR). `return` is `ARETURN`; classes load lazily through a per-compile `ScriptClassLoader`. Error lines come from the innermost stack frame of the script's classes with a line number.
- **Scoping** (`runtime` package): `Scope<T>` interface with `Slot` holders (`set` initialises, `assign` requires the slot to be set); `Namespace` is the main implementation (`child`, `enterPackage`, `declare`, `initialize`, `assign`, `lookup`). Packages are namespaces; objects are not (they are `BabbleInstance`s). A package changes only through its own code (`n = v` in its body or its functions): `p.n = v` from outside fails with `Cannot assign to a package member : n`, from `Members.assign` at runtime (which tries a `Namespace` before Java targets, since `isJavaObject` would take it for one) and from `TypeChecker.assignedMemberType` when the package is known statically.
- **Natives**: built-ins implement `runtime.Callable`.
  - Native functions live in `impl.natives`: `print` writes to the `ScriptContext` writer, or `to:` any `Appendable`; `same`; `classof`; `ConvertFunction`, `int(x)` truncating towards zero and failing out of range, `double(x)`, both parsing strings, typed `int`/`double` by `TypeChecker.implicitType`.
  - Java interop lives in `impl.natives.java`: `JavaPackage` → `JavaClass` (a `JavaType`, equal by `Class`; members are public member classes, methods, then public fields: static final ones cached as constants, others read on each selection and never cached by `Bootstrap`, `isConstant`; instance fields only through an instance, `value(receiver, name)`; `assign` writes a public non-final field, `Members.assign` sending Java targets there, and refuses a Babble function for a functional-interface field, which needs `Runnable(f)` since member assignment has no `ScriptRuntime`) → `JavaMethod`/`BoundJavaMethod`/`JavaObject` (a `JavaValue` wrapper for objects Babble constructs, printing as its value).
  - Java calls return objects unwrapped; `Members.select` gives any Java object other than Babble's own values (null, `Integer`, `Double`, `Boolean`, `String`, callables) its members through `JavaObject.member`, and `Overloads.resolveMethod` calls a method of an inaccessible class (`List.of()`'s) through the accessible type it comes from (`JavaTypes.accessible`). The type checker types a Java result or static field as `JavaInstance` of its class, except interfaces, arrays and inaccessible classes (`dynamic`). Calling a functional interface's class with one Babble function converts it explicitly.
- **Formatter** (`org.babblelang.format.Formatter`, command line `-format`, `org.babblelang.Babblefmt`): works on the token stream, comments included (the lexer puts them on the hidden channel, so the parser never sees them; anything counting tokens must look at the channel, as `BabbleSession.classify` does).
  - It reads in the parse tree (`BabbleScriptEngine.parseSource`) what each token is: a call's `(` or a block's, a newline that separates expressions (`sep`), continues one (+1 indent), sits in a parenthesised list, or precedes a block/`else`/`static` (dropped unless a comment is in the way). It keeps the source's line breaks otherwise; indentation comes from a stack of open parentheses, each anchored to the line where its `if`/function/class starts.
  - The result is parsed again and must give the same tree, newlines and semicolons aside (`IllegalStateException` otherwise). Note that `;;( … ;;)` closed on its line and followed by code lexes as a line comment (longest match).

## Known issues

- Reading a package member walks out of the package: `def x = 1 ; package p ( … ) ; p.x` is `1` (`Members.select` uses `Namespace.get`, which searches enclosing scopes), and the type checker types it `dynamic`.
- The interpreter cannot run a script's functions on several threads (it keeps the current scope in a field): the fable ray tracer, which renders on 16 threads, only runs in compiled mode.

## Tests

Tests live in `src/test/java/org/babblelang/tests`. Most extend `BabbleTestBase`, which offers `interpret(String)` for inline snippets and `interpretFile(String path)` for `.ba` scripts. End-to-end language tests are `.ba` files in `src/test/babble/` (referenced by relative path, so tests must run from the repo root, as Maven does). In-language `assert(...)` calls are the assertion mechanism inside `.ba` scripts.

- Both modes: `DifferentialTestCase` runs every `.ba` file and a list of snippets in both modes and compares results, output and errors.
- Modules: `BabbleModulesTestCase` covers modules, in a `MapModuleSource`; `FileModulesTestCase` what is particular to files (real paths, symbolic links, absolute paths), rooted file sources and class path modules; `ModuleSourcesTestCase` the `ModuleSource` contract (an in-memory source that records what it is asked); and `src/test/babble/Modules.ba` with the fixtures in `src/test/babble/modules/`.
- Object model: `BabbleObjectModelTestCase` and `BabbleJavaObjectsTestCase` (§10 of its design doc).
- Compiler and analysis: `BabbleCompilerTestCase` covers compiled-mode specifics (method names, generated classes, stack-trace lines, class verification, method/constant splitting); `ResolverTestCase` has golden tests of name bindings; `TypeCheckerTestCase` has golden tests of type diagnostics (`line:column message`) and checks every `.ba` script checks cleanly; `RuntimeBoundaryTestCase` keeps the runtime free of the front end.
- Sessions: `ReplTestCase` covers sessions (shadowing, static checks and types across inputs, modules loaded once per session), `classify`, and the loop's transcripts.
- Formatter: `FormatterTestCase` has golden tests of the formatter and checks every `.ba` script of the repository formats to a fixed point; `org.babblelang.BabblefmtTestCase` covers its command line.
- Examples: `ExamplesTestCase` compiles every script of `examples/` without running it (the ray tracers take minutes to run): with `compileProgram` and its static imports in the compiled run, through `compile()` (parse, analysis, type checking) in the interpreted one.
- Command line and babblec: `org.babblelang.MainTestCase` covers the command line (scripts, arguments, `-keep-alive`, `-compile`, exit statuses); `BabblecTestCase` compiles programs into jars and runs them in fresh JVMs with the jar alone (output, arguments, errors, dynamic imports, contents, byte-identical rebuilds), and with Babble on the class path (`runWithBabble`: modules compiled while running, the root).
