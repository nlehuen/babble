# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Babble is a toy programming language running on the JVM, built as a learning project for parsing/interpreting/compiling. It uses ANTLR4 for parsing and runs either interpreted directly on the ANTLR parse tree (the default) or compiled to JVM bytecode with ASM (`-Dbabble.mode=compile`). Java 21 source level, JUnit 5 (Jupiter) for tests. The compiler follows `docs/design/bytecode-compiler.md` (phases 1 and 2 done; §16 and §17 there list what landed).

## Commands

- Build & test: `mvn package` (CI runs `mvn -B package` on JDK 21). Surefire runs the suite twice: `default-test` (interpreter) and `compiled-tests` (`babble.mode=compile`, plus `babble.verify=true` so every generated class passes ASM's `CheckClassAdapter`; reports in `target/surefire-reports-compiled`).
- Run tests only: `mvn test`
- Run a single test class: `mvn test -Dtest=BabbleFunctionsTestCase`
- Run a single test method: `mvn test -Dtest=BabbleFunctionsTestCase#methodName` (runs in both modes)
- Compiler debugging switches (system properties): `babble.dumpClasses=<dir>` writes the generated `.class` files for `javap -c -p`, `babble.trace=true` prints an ASM listing, `babble.verify=true` runs `CheckClassAdapter`.
- Benchmarks (not a test): `org.babblelang.bench.Benchmarks` in the test sources, run from the repo root.

### Local toolchain, and podman for CI parity

Maven and a JDK are installed on the host via Homebrew (`/home/linuxbrew/.linuxbrew/bin`), so plain `mvn ...` works and is the fastest way to build and test.

Note the version gap: the host JDK is **26**, CI runs **21**. The build sets `release 21`, so compilation is checked against the right API level either way, but tests execute on whichever JVM runs them. To reproduce CI exactly — or to check a failure that might be JVM-version-specific — run Maven in a container instead, substituting any `mvn ...` command:

```
podman run --rm -v /var/home/nlehuen/babble:/work:z -v ~/.m2:/root/.m2:z -w /work \
    docker.io/library/maven:3.9-eclipse-temurin-21 mvn -B clean test
```

The image matches CI's JDK 21; mounting `~/.m2` caches dependencies between runs, and the `:z` volume flags are required for SELinux.

The ANTLR lexer/parser/visitor classes (`org.babblelang.parser.*`) are **generated** by the `antlr4-maven-plugin` into `target/generated-sources/antlr4` from `src/main/antlr4/org/babblelang/parser/Babble.g4`. Never edit generated parser code; change the grammar and rebuild. Grammar changes require `mvn generate-sources` (or any build) before the new contexts are visible to Java code.

## Architecture

The pipeline is: Babble source → ANTLR4 parse tree → block scope analysis → tree-walking interpreter *or* bytecode compiler. There is no separate AST; both backends work on ANTLR `ParserRuleContext` nodes directly.

- **Grammar** (`src/main/antlr4/.../Babble.g4`): ~100 lines defining the whole language. Everything is an `expression` (no statements); labeled alternatives (`# defExpression`, `# call`, etc.) become the visitor methods. Visitor generation is on, listener off. Newlines are significant: `NL` tokens (with `;`) separate statements, and `NL*` is permitted only after continuation tokens (binary operators, `,`, `=`, `->`, `then`, `else`) — never between an expression and a following `(`, which would recreate the call/juxtaposition ambiguity.
- **Engine entry point** (`org.babblelang.engine`): JSR-223 (`javax.script`) implementation. `BabbleScriptEngineFactory.INSTANCE` → `BabbleScriptEngine` (lexes/parses, runs the analysis, `Compilable`). `getMode()` picks `INTERPRET` (`BabbleCompiledScript`) or `COMPILE` (`compiler.CompiledBabbleScript`) from the `babble.mode` engine attribute or system property. The engine's constructor registers built-in "implicits": `print`/`println`, `assert`, `import`, and the `java`/`javax` root packages (several have French aliases, e.g. `suppose`, `affiche`). `createRuntime(ScriptContext)` builds each eval's namespaces: implicits → `STDOUT` (the context writer) → script root (ENGINE_SCOPE bindings + top-level defs).
- **Analysis** (`org.babblelang.analysis`): runs in both modes at `compile()` time. A third pass, `Resolver` (result: `ScopeAnalysis.resolution()`), binds every name to a frame `Variable` or to a runtime lookup; only the compiler uses it. `BlockScopes` (pass 1) computes each scope's `def`s for hoisting and the members of classes, objects and interfaces (`TypeNode`), and checks placement (`return`, `this`, `super`, `private`, header `def`s, value-class rules). `TypeChecks` (pass 2) resolves `implements`/`extends` statically (interface literals or Java interfaces), checks completeness, default conflicts, Java arities and `super`, and reports private/read-only access when the receiver's class is statically known. Results live in `ScopeAnalysis` (declared names, `ClassShape`s, def targets, super targets, warnings). Errors become `ScriptException`s worded like runtime ones; warnings go to the context's error writer.
- **Block scope**: the file, function literals (parameters + body top level), packages, and every other block (block expression, `if` branch, `while` body — fresh per iteration) are scopes. Names a scope defines are declared (unset) on entry; reading or assigning them before their `def` runs fails with `Name used before definition`. Blocks that define nothing get no namespace. Top-level `def`s of class, object, interface and static bodies declare *members*, which bind no unqualified name.
- **Object model** (`docs/design/object-model.md`): `class (params) implements I ( body ) static ( … )`, `value class`, `interface extends … ( … )`, `object implements … ( … )`, `this`, `super.m()`/`super(I).m()`, `x is T`, `private`, and the natives `same`/`classof`. Members are reached only as `this.x` or `obj.x`; `this.x` goes through `Members.selectOwn`/`assignOwn`, the only path that may see private members. Runtime: `BabbleClass` (callable class value, statics, inherited defaults), `BabbleInstance` (member array, value-class equality/hash/`toString`), `BabbleInterface`, `ClassShape` (static description, string-encoded for compiled code), `Classes` (helpers both backends call), `Supers`. Java boundary: `Values.toJava`/`fromJava`, `Faces` (proxies for instances implementing Java interfaces and for functions converted to functional interfaces), `Overloads`/`JavaTypes`.
- **Runtime** (`org.babblelang.runtime`, no ANTLR dependency): everything both backends call — `Operators`, `Truth`, `Members`, `Arguments` (the one implementation of argument binding), `Calls`, the `Callable` calling convention `call(ScriptRuntime, Object[] args, String[] names, CallSite)`, `BabbleFunction`/`BoundMethod`, `CompiledFunction`/`FunctionBody`, `CallSite`/`OpSite` (source texts for error messages), and `ScriptRuntime` (per-eval root namespace, `ScriptContext`, engine).
- **Interpreter** (`org.babblelang.engine.impl.Interpreter`): extends the generated `BabbleBaseVisitor<Object>`; one `visitX` method per grammar alternative. It tracks the `last` visited context so `BabbleCompiledScript` can report the line number on error. `return` is a `ReturnException` caught by `Function.invoke`. Class constructors are `InterpretedClassBody`.
- **Compiler** (`org.babblelang.compiler`): `CodeGenerator` emits a script class (`org/babblelang/generated/Script$N`): `run(ScriptRuntime, Namespace)` (split into `run$k` when large), one `fn$N$name` static method per function literal (wrapped as `FunctionBody` via `LambdaMetafactory`), one `cls$N$Name` constructor per class/object expression (wrapped as `ClassBody`), and static constant fields built in `<clinit>` helpers. Phase 2: function, block, class-body and static-block variables are JVM locals, or `Cell`s when captured (function and class values carry their captured cells); the file, packages, interface bodies and any scope declaring a `package` keep phase 1 namespaces. Each class/object expression whose body keeps no namespace also gets its own JVM class `Script$N$k$Name extends BabbleInstance` (a field per member, methods as instance methods behind shared `CompiledMethod`s, hidden `$v$x` fields for constructor cells methods capture); `this.x`/`this.m()` compile to `GETFIELD`/`PUTFIELD`/`INVOKEVIRTUAL`. Invariants: every expression leaves exactly one `Object` on the stack, and the operand stack is empty at loop heads (HotSpot OSR). `return` is `ARETURN`; classes load lazily through a per-compile `ScriptClassLoader`. Error lines come from the innermost stack frame of the script's classes with a line number.
- **Scoping** (`impl` package): `Scope<T>` interface with `Slot` holders (`set` initialises, `assign` requires the slot to be set); `Namespace` is the main implementation (`child`, `enterPackage`, `declare`, `initialize`, `assign`, `lookup`). Packages are namespaces; objects are not (they are `BabbleInstance`s).
- **Natives**: built-ins implement `runtime.Callable`. Native functions live in `impl.natives` (`print` writes to the `ScriptContext` writer, or `to:` any `Appendable`; `same`; `classof`); Java interop lives in `impl.natives.java` (`JavaPackage` → `JavaClass` (a `JavaType`, equal by `Class`) → `JavaMethod`/`BoundJavaMethod`/`JavaObject` (a `JavaValue` wrapper)). Calling a functional interface's class with one Babble function converts it explicitly.
- **Optimizers** (`org.babblelang.engine.optimizer`): visitors that rewrite the parse tree in place. `OptimizerBase` provides a `replace()` helper to swap one context node for another; `SimpleBinaryOpsOptimizer` is the example (constant folding of binary ops). The engine does not run them.

## Tests

Tests live in `src/test/java/org/babblelang/tests`. Most extend `BabbleTestBase`, which offers `interpret(String)` for inline snippets and `interpretFile(String path)` for `.ba` scripts. End-to-end language tests are `.ba` files in `src/test/babble/` (referenced by relative path, so tests must run from the repo root, as Maven does). In-language `assert(...)` calls are the assertion mechanism inside `.ba` scripts. `DifferentialTestCase` runs every `.ba` file and a list of snippets in both modes and compares results, output and errors; `BabbleObjectModelTestCase` and `BabbleJavaObjectsTestCase` cover the object model (§10 of its design doc). `BabbleCompilerTestCase` covers compiled-mode specifics (method names, generated classes, stack-trace lines, class verification, method/constant splitting); `ResolverTestCase` has golden tests of name bindings.
