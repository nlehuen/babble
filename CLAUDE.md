# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Babble is a toy programming language running on the JVM, built as a learning project for parsing/interpreting/compiling. It uses ANTLR4 for parsing and runs either compiled to JVM bytecode with ASM (the default) or interpreted directly on the ANTLR parse tree (`-Dbabble.mode=interpret`; the interpreter is the reference implementation the compiler is tested against, and is single-threaded). Java 21 source level, JUnit 5 (Jupiter) for tests. The compiler follows `docs/design/bip001_bytecode-compiler.md` (`BIP001-P1`–`BIP001-P3`, `RM001` typed primitive lowering & static dispatch, and `RM003` JVM interfaces & proxy-free Java adapters landed in §16–§20; phase 4, ahead-of-time compilation into a jar, was done as `BIP006-P4`–`P6` in `docs/design/bip006_module-sources-and-aot.md`).

## Commands

- Build & test: `mvn package` (CI runs `mvn -B package` on JDK 21). Surefire runs the suite twice: `default-test` (`babble.mode=interpret`, set explicitly since compile is the default) and `compiled-tests` (`babble.mode=compile`, plus `babble.verify=true` so every generated class passes ASM's `CheckClassAdapter`; reports in `target/surefire-reports-compiled`).
- Run tests only: `mvn test`
- Run a single test class: `mvn test -Dtest=BabbleFunctionsTestCase`
- Run a single test method: `mvn test -Dtest=BabbleFunctionsTestCase#methodName` (runs in both modes)
- Run `.batest` systematic tests: `mvn -q test -Dtest=BatestTestCase -Dbatest.filter=<file-or-pattern>` (fast dual-mode inner loop without JaCoCo; append `#N` or `:line` for a single case), or `mvn -q verify -Pbatest` (full dual-JVM JaCoCo coverage report in `target/batest-report/`; combine with `-Dbatest.filter=...` and `-Dbatest.inspect=<Class>` for scoped hotspot inspection).
- Type checker: always on; strict static typing is the only mode (`any` / `any?`, unions `A | B`, nullables `T?`, generics with `(...)` syntax, `as`, call-site parameter inference for non-exported/non-escaping callables, required annotations on exports/escapes/interfaces/uncalled functions, full reassignment inference), and all type check failures are errors. Diagnostics go to the context's error writer (`Error : ...` with line and column), the first one fails `compile()` with `TypeCheckException`; runtime `Types.check` remains only at `as` casts and external boundaries (Java boundaries via `JavaTypes` and Java generic `TypeVariable`/`WildcardType` returns/fields, plus `BabbleInstance`/`BabbleType.setMember`), with `Values.widen` for numeric widening (`int`→`double`, `byte`→`int`...; P5–P7, `BIP011-P2a`).
- Compiler debugging switches (system properties): `babble.dumpClasses=<dir>` writes the generated `.class` files for `javap -c -p`, `babble.trace=true` prints an ASM listing, `babble.verify=true` runs `CheckClassAdapter`.
- Command line, after `mvn package` (main class `org.babblelang.Main`; the jar's manifest points at `target/lib`, filled by `maven-dependency-plugin`; `-Dbabble.mode` applies):
  - `java -jar target/babble-1.0-SNAPSHOT.jar` starts the interactive mode; `… script.ba [arguments...]` runs a script (arguments in the `args` list; exit status 1 if it fails, 2 for a bad command line); `… -keep-alive script.ba` continues in the interactive mode after it.
  - `… -compile main.ba [-o app.jar] [-root dir]` is `babblec` (ahead-of-time compilation, `docs/design/bip006_module-sources-and-aot.md` §5): it writes a jar of the program, its static imports and a copy of the runtime, which `java -jar app.jar [arguments...]` runs on a plain JRE (exit 0, 1 if it fails to compile, 2 for a bad command line). With Babble on the class path (`java -cp app.jar:target/babble-1.0-SNAPSHOT.jar org.babblelang.runtime.Launcher …`), dynamic imports of modules the jar lacks are compiled from the program's root (`-Dbabble.root=dir`, else the index's, relative to the jar).
- Formatter: `java -jar target/babble-1.0-SNAPSHOT.jar -format [-w] [-l] [-check] [file.ba | directory]...` (no file: standard input to standard output). `Main` hands what follows `-format` to `org.babblelang.Babblefmt.run`; exit status 1 for a file that can't be formatted or, with `-check`, isn't; 2 for a bad command line. Every `.ba` file of the repository must be formatter-clean: `-format -check src/test/babble examples` (`FormatterTestCase` fails otherwise; `-format -w` fixes it).
- Benchmarks (not a test): `org.babblelang.bench.Benchmarks` in the test sources, run from the repo root.

The ANTLR lexer/parser/visitor classes (`org.babblelang.parser.*`) are **generated** by the `antlr4-maven-plugin` into `target/generated-sources/antlr4` from `src/main/antlr4/org/babblelang/parser/Babble.g4`. Never edit generated parser code; change the grammar and rebuild. Grammar changes require `mvn generate-sources` (or any build) before the new contexts are visible to Java code.

### Toolchains

Any JDK 21+ and Maven 3.9 build Babble; `java -version` and `mvn -v` tell what a machine has (CI and the cloud sessions run JDK 21). The build sets `release 21`, so compilation is checked against the right API level whatever the JDK, but tests execute on whichever JVM runs them.

On the maintainer's workstation, Maven and a JDK **26** come from Homebrew (`/home/linuxbrew/.linuxbrew/bin`). To reproduce CI exactly there — or to check a failure that might be JVM-version-specific — run Maven in a container, substituting any `mvn ...` command:

```
podman run --rm -v /var/home/nlehuen/babble:/work:z -v ~/.m2:/root/.m2:z -w /work \
    docker.io/library/maven:3.9-eclipse-temurin-21 mvn -B clean test
```

## Conventions

- **Wording**: error messages, warnings and commit subjects put a space before a colon (`Not a number : x`, `Operator methods : a + b calls a.plus(b)`). Type diagnostics are worded like the runtime errors they predict, and both modes report the same message.
- **A language change** goes through every stage that sees the syntax: the grammar, the analysis passes (`BlockScopes`, `TypeChecks`, `Resolver`, `TypeChecker`), both backends (`Interpreter`, `CodeGenerator`), and the formatter (spacing, newlines). It comes with tests: a `.ba` script in `src/test/babble/` (run in both modes, type-checked and format-checked automatically), `DifferentialTestCase` snippets for its errors, and goldens in `TypeCheckerTestCase` / `FormatterTestCase` where they apply.
- **Docs move with the code**: the README (its tour, and the checklists at the end: *Implemented*, *Planned*, *lessons from the ray tracer*), this file, and the design doc of the area are updated in the same change. `examples/` is compiled by the suite (`ExamplesTestCase`) but not run; after a change that could affect them, run a ray tracer by hand (see the README; argon must still render `examples/raytracer-argon/scene.ppm` byte for byte).
- **Roadmap (`RM###`) references**: outside `docs/design/README.md`, only **past (implemented)** `RM###` milestones may be mentioned, with the sole exception of a PR or commit description that is directly implementing that `RM###` (e.g., mentioning `RM999` in a PR or commit description directly implementing `RM999` is fine). Never mention unimplemented `RM###` identifiers anywhere else — not in code or tests, not in other docs (`CLAUDE.md`, `README.md`, `docs/design/bip*.md` — use `BIP###` / `BIP###-P#` instead), and not in unrelated PR or commit descriptions — so the future part of the roadmap can be modified, merged, split, or reordered at will.
- **Commits** that fix an issue say `Fixes #N` in their message.

## Git and pull requests

- Work on a branch, never directly on `master`. Rebase it onto `origin/master` before opening a pull request.
- Pull requests are merged as new commits (rebase or squash), so a merged branch's commits are not ancestors of `master`: start the next change from a fresh `origin/master`, not from the old branch.
- Always watch a pull request after creating it (subscribe to its activity): follow its CI and reviews and fix what fails, without asking first.

## Architecture

The pipeline is: Babble source → ANTLR4 parse tree → analysis → tree-walking interpreter *or* bytecode compiler. There is no separate AST; both backends work on ANTLR `ParserRuleContext` nodes directly.

- **Grammar** (`src/main/antlr4/.../Babble.g4`): ~100 lines defining the whole language. Everything is an `expression` (no statements), plus top-level/block `effectDeclaration` (`axiom` / `impure`) rules; labeled alternatives (`# defExpression`, `# call`, etc.) become the visitor methods. Visitor generation is on, listener off, and contextual `ID` predicates disambiguate effect/algebraic keywords (`axiom`, `impure`, `pure`, `hermetic`, `mut`, `borrow`, `deterministic`, `nothrow`, `idempotent`, `commutative`, `associative`, `monotone`, `injective`) so they remain valid variable, parameter, and member names.
  - Newlines are significant: `NL` tokens (with `;`) separate statements, and `NL*` is permitted only after continuation tokens (binary operators, `,`, `=` and the compound `+=`/`-=`/`*=`/`/=`, `->`, `then`, `else`) and before a selector's `.` or `?.` (a line may start with `.` or `?.`; `.5` lexes as a number).
  - Never between an expression and a following `(`, which would recreate the call/juxtaposition ambiguity, nor before a unary `-` (`# negate`, binding tighter than binary operators; a negated integer literal is folded, so `-2147483648` is an int), so `a` then `-b` on the next line are two expressions.
  - The 17 core type names (`byte`..`string`, `list`..`entry`, `any`, `void`; `BIP011-D11`) are lexer keywords (`BYTE_KW`..`VOID_KW`, contiguous for `BabbleLexer.isCoreTypeKeyword`), so no `def`, parameter, type parameter or package can take one. The lexer turns one that follows `.` or `?.` back into an `ID` (its `nextToken`), so selectors, qualified assignments and effect targets accept them as member names (`xs.set`, `stream.map`). In types they are `# coreType`; as expressions `# coreTypeName` (a scalar's conversion function, or the right of `is`). Literals : `INT`, `LONG_LIT` (`42L`), `FLOAT_LIT` (`1.5f`), `DOUBLE_LIT` (`1.5`, `1e3`, `2d`), `CHAR_LIT` (`'a'`), with escapes in characters and strings (`Interpreter.unescape`). Postfix `e!` (`# nonNullAssertion`, token `BANG`, no newline before it) asserts non-null. Explicit type arguments (`BIP011-D9`): `expression typeArguments` is `# typeApplication` only when the parentheses hold a `?` or `|` (`isTypeApplicationStart`, `Box(int?)`); names only, `Box(int)(x)`, parse as a call, which `TypeChecker` makes a type application when its callee is generic and its arguments reread as types (`reparseTypeArguments`, tried `quietly`), recording it (`ScopeAnalysis.isTypeApplication`) so both backends evaluate it as its callee; `add(a)(b)` with a value `a` stays a call.
  - `else if` is a second `# ifExpression` alternative ending with `elseIf=expression` (a predicate requires `if` next): ending the alternative makes ANTLR parse it at the `if`'s precedence, so `… else (c) + 1` applies to the whole chain.
- **Engine entry point** (`org.babblelang.engine`, `org.babblelang.effects`): JSR-223 (`javax.script`) implementation. `BabbleScriptEngineFactory.INSTANCE` → `BabbleScriptEngine` (lexes/parses, runs the analysis, `Compilable`, plus compile-time host effect configuration: `allowAxioms`, `allowsAxioms`, `assumeEffects`, `assumeConstructorEffects`, `markImpure`). `org.babblelang.effects` provides the public `Effect` enum and `@Pure`..`@Impure` runtime annotations for host Java classes, constructors, methods, and parameters. `getMode()` picks `COMPILE` (`compiler.CompiledBabbleScript`, the default) or `INTERPRET` (`BabbleCompiledScript`) from the `babble.mode` engine attribute or system property.
  - The built-in "implicits" (`print`/`println`, `assert`, `import`, `same`, `classof`, and the `java`/`javax` root packages; French aliases `affiche`/`afficherc`, `suppose`, `importe`) come from `runtime.Implicits.create()`. The conversions (`int(x)`, `long(x)`...) are not names : they are the core type keywords as values (`# coreTypeName`, `ConvertFunction.of`).
  - `createRuntime(ScriptContext)` builds each eval's namespaces: implicits → `STDOUT` (`Implicits.withOutput`, the context writer) → script root (ENGINE_SCOPE bindings + top-level defs), and its `Modules` (the engine's `EvalModules`: the eval's loaded modules, compiled through the module cache).
- **Sessions and the REPL** (`docs/design/bip004_repl.md`): `BabbleSession` (`engine.newSession(context)`) evaluates successive inputs that see each other's definitions.
  - Each input that defines names or packages is a scope *nested* in the previous one, in the analysis (`AnalysisSession`: chained file `ScopeNode`s, plus the type nodes, definition/occurrence scopes, reassigned defs, and committed `RM002` callable/Java effect summaries the passes look up; `BlockScopes.analyze(file, session)` then `session.commit(analysis)`) and at runtime (a child `Namespace`; scripts run in a given namespace through `BabbleScript.eval(ScriptRuntime)`, the base class of both script kinds). So a redefinition shadows, earlier code keeps its definitions, and nothing static is weakened.
  - The session keeps one `Modules` for its lifetime, so a module imported by several inputs is loaded once. `BabbleSession.classify` tells `EMPTY`/`INCOMPLETE`/`COMPLETE` inputs apart from where the parser fails (`ParseFailure.atEnd`).
  - `org.babblelang.Repl` is the loop on top: prompts, multi-line input, `:help`/`:cancel`/`:quit`, values shown (strings quoted), errors printed without ending the loop. `org.babblelang.Main` is the command line: it runs a script as the first input of a session (`BabbleSession.eval(source, sourceName)`), binds `args` (`JavaObject.of(list)`), and starts the loop when there is no script or with `-keep-alive`.
  - Parsing is shared with `compile()` (`BabbleScriptEngine.parse`), which reports `Syntax error : unexpected …` with line and column; type diagnostics throw `TypeCheckException`.
- **Analysis** (`org.babblelang.analysis`): runs in both modes at `compile()` time, in four passes, in this order (`BlockScopes.analyze`):
  1. `BlockScopes` computes each scope's `def`s for hoisting, standalone `effectDeclaration`s, and the members of classes, objects and interfaces (`TypeNode`), and checks placement (`return`, `this`, `super`, `private`, header `def`s, value-class rules).
  2. `TypeChecks` resolves `implements`/`extends` statically (interface literals or Java interfaces), checks completeness, default conflicts, Java arities and `super`, and reports private/read-only access when the receiver's class is statically known.
  3. `Resolver` (result: `ScopeAnalysis.resolution()`) binds every name to a frame `Variable` or to a runtime lookup; only the compiler uses it.
  4. `TypeChecker` + `EffectChecker` (`docs/design/bip003_type-system.md`, `docs/design/bip008_static-typing.md`, `docs/design/bip007_effects.md`, `docs/design/bip010_type-checker-simplification.md`) run static typing over `Type` (`any`, the scalars `byte`..`double` (`Type.NUMBERS`, in widening order), `bool`, `char`, `string`, `null`, nullable `T?`, union `A | B`, `TypeVar`, effect-annotated function types `Type.Function` with `EffectSet` and `mut`/`borrow` parameters, nominal/parameterized class/interface instance types with `(...)` syntax, class values, packages, Java classes, interfaces and arrays) using package-private collaborators (`BIP010` §7): `TypeAlgebra` (an instance bound to a small `Env`: relations, `ConstraintStore`, overlap, casts, narrowing, joins, projections, substitution), `TypeAnnotations` (what annotations denote, type variables, declared types), `MemberTypes` (member resolution and interface conformance), `OperatorTypes` (operators, operator methods, implicits), `CallSolver` (call dispatch and generic/SAM/Java/operator solving; it keeps the Java executable each call resolves to), `JavaTypeBridge` (all `java.lang.reflect`: translation, with `JavaNullness` for nullness annotations and the `java.base` overlay, wildcard containment, SAMs, accessibility, `mostSpecific`, Java members; `TypeChecker` imports no reflection), `Narrowing` + `TypeEnv` (refinements and persistent occurrence-typing environments), `SlotInference` (Tarjan-ranked worklist and `SlotCell`s: the only inference engine), `TypedProgram` (the queries `EffectChecker` makes, reading narrowed occurrence types rather than narrowing again), `LoweringAnalyzer` (post-convergence `RM001`/`RM003`/`T9` metadata, deriving every static target from the converged types), `StaticRefs` (static singletons), and `TypedModuleSummary`/`ImportedSummaries` (AST-detached module and session summaries, and the one lookup of them). `TypeChecker.run` converges the slots, infers effects, re-converges once, then makes a single verification walk; expressions go through an explicit `typeOf(ctx, expected, role)` dispatch, and every numeric widening (`int`→`double`, `byte`→`int`...) is recorded by `coerce`, as a mask of the target numbers (`TypeAlgebra.wideningMask`). Features include generic call/constructor inference and covariance, call-site parameter inference (P7) for non-exported/non-escaping/non-interface callables, inference for unannotated defs and members across their assignments via Tarjan lexical SCCs + monotone `SlotCell` worklist convergence, flow-sensitive narrowing (`is`, `else` subtraction, `== null`/`!= null`/`<> null`/truthiness, `while` loops), safe navigation `?.`, Tarjan SCC bottom-up fixed-point effect/algebraic inference & verification (`RM002` / `BIP007-P1`: `pure`, `hermetic`, `mut`, `borrow`, `deterministic`, `nothrow`, `idempotent`, `commutative`, `associative`, `monotone`, `injective`, `@PARAM`/`@THIS` alias tracking, static call-site `mut` exclusivity, frame-local `borrow` closures, bounded call-site specialization, and the 7-tier `axiom`/`impure`/Java annotation resolver), and diagnostics (`ScopeAnalysis.typeDiagnostics()`) worded like the runtime errors they predict.
  - Numbers (`BIP011-P2a`): a number widens along `byte -> short -> int -> long -> float -> double` (`TypeAlgebra.relate`, `widestNumber` for joins); arithmetic promotes as Java does (`OperatorTypes.arithmeticResult`/`divisionResult`, `Operators` at runtime); `char` is not a number. An integer or decimal literal gets its contextual type in `TypeChecker.integerLiteral`/`visitDouble`, which records a value of another type than `int`/`double` (`ScopeAnalysis.literalValue`: a `Byte`, a `Long`...) for both backends. The new numbers stay boxed in compiled code (`PrimitiveKind` has only `INT`/`DOUBLE`/`BOOL`).
  - Runtime checks (P5–P6b): `TypeChecker` records `ScopeAnalysis.widening(ctx)` (a mask of numeric ranks; `widensToDouble` when it is `double` alone) wherever a number widens (parameters, returns, `def`s, assignments, `if`/`while` joins), both backends converting with `Values.widen`, and records `ScopeAnalysis.checkedType(ctx)` for `as` casts and for Java generic calls/field reads whose reflection type is a `TypeVariable`/`WildcardType` resolving to a non-`any?` type (supporting `union`, `null`, `any`, and non-nullable `Builtin`/`FunctionType`/`JavaClassType`/`NominalType` with an id per class/interface expression: in a module, its key and the type's name, `lib/vec3.ba#Vec3`, stable across compilations; elsewhere JVM-unique, `T17`). `ClassShape` retains declared member and static types for `BabbleInstance`/`BabbleType.setMember` (used by external Java writes and `any` writes), while Babble-side `this.x = …` direct field writes in `CodeGenerator` omit checks. Java nullness (`BIP011-P3`): `JavaNullness` decides what a Java method returns or a field holds — non-null (a primitive, `@NotNull`/`@NonNull` annotations matched by name, `@NullMarked` scopes, or the `java.base` overlay: `String`, `StringBuilder`, `Math`, collections but `Map.get`...), parametric (`List.get` is `T`), else nullable — and `JavaTypeBridge.javaResult` types it so (`Integer.getInteger` is `int?`); a result typed non-null is checked where it enters Babble (`checksResult` → `checkedType`, `Type error : expected string, got null`), since `@NotNull` is soft. Boxed results are no longer rejected when null (no outbound `checkBoxed`); compiled Java-interface bridges reject a null boxed argument only for a non-null primitive Babble parameter, and `JavaTypes.checkParameters` (in `Faces`) checks arguments entering Babble from Java interfaces.
  - Results live in `ScopeAnalysis` (declared names, `ClassShape`s, def targets, super targets, warnings with line and optional column, type diagnostics, `RM001`/`RM003` converged facts published by `LoweringAnalyzer` (`PrimitiveKind` per expression/declaration, definite-initialization flags, and static `JavaCallTarget`/`JavaConstructorTarget`/`JavaFieldTarget`/`BabbleCallTarget`/`ModuleExportTarget`/`InterfaceCallTarget`/`IsTarget` targets), plus `RM002` callable and call-site `EffectSet` summaries). Non-typecheck warnings go to the context's error writer as `Warning : ...`, type diagnostics as `Error : ...`; errors become `ScriptException`s worded like runtime ones.
- **Modules** (`docs/design/bip005_modules.md`): `export def x = …` / `export package p ( … )` (top level of a file only, checked by `BlockScopes`; names in `ScopeAnalysis.exports()`) and `import("path.ba")`.
  - Loading: `ImportFunction` sends names ending in `.ba` to `BabbleScriptEngine.importModule`, which goes through the runtime's `Modules` to the engine's `EvalModules.load`. The engine's `ModuleSource` (*M4*, `docs/design/bip006_module-sources-and-aot.md` §4; the `babble.moduleSource` attribute, default `FileModuleSource.INSTANCE`; also `FileModuleSource.rooted(dir)`, `MapModuleSource`, `ClassPathModuleSource`, sharing `LogicalPaths` for `/`-separated paths) resolves the name from the importing module (a `ModuleId`: key + display name; the importer's source name maps back to it through `compiledAs`, else `ModuleSource.identify`, which for files accepts a `FILENAME` that does not exist).
  - Running: the module is compiled in the engine's mode and run once per eval on a `ScriptRuntime` of its own (own root namespace, same context and bindings, the eval's loaded modules keyed by `ModuleId.key`). The result is a `runtime.Module`: a read-only `HasMembers` view (plus `exportAt(int)` indexed access for `RM001`) of the exported names of that root, registered before the file runs so that cycles work. No backend has module-specific code: both script classes extend `BabbleScript` (`eval(ScriptRuntime)`, `exports()`).
  - *Static imports* (M2): pass 1 records each `import("….ba")` call with a string literal (`BlockScopes.imports`); after pass 1, `BlockScopes.analyze(…, ModuleLoader)` hands the file's `ModuleInterface` (exported names) to the loader (`started`, for cycles), then loads each import's interface (`load`; the engine's `Loader`, relative to the importing file), and `TypeChecks` resolves `implements`/`extends`/`super(I)` paths through modules (`resolveDefinition`, `moduleOf`, the exporter's `resolveExport`) and reports `No such export` / `Cannot assign to an export` (errors).
  - The module cache (`compiledModule`, under `moduleLock`) keys by `ModuleId.key` and keeps a module's compiled script and interface while the source, the mode and the version (`ModuleSource.version`; a content hash for files) of every module its analysis read are unchanged; runtime `import` goes through it too.
  - *Types across modules* (M3): a static import's type is `Type.Module`, whose members are the exporter's types; the `ModuleInterface` carries the exporter's AST-detached `TypedModuleSummary` once it ran (`typed`, read with `summary()`; `BlockScopes` keeps it as `pass.summary`, never the `TypeChecker`), so importers query lock-free exported types, declarations, members, and `CallableEffectTemplate`s without retaining the exporter's `TypeChecker`. Annotations naming a class through a module (`shapes.Circle`, or an alias of it) are nominal `Instance` types (`typeThroughModule`). Reading an export of a file still being analysed in an import cycle reports `Missing type : <name> (import cycle with <module>)`.
- **Block scope**: the file, function literals (parameters + body top level), packages, and every other block (block expression, `if` branch, `while` body — fresh per iteration) are scopes. Names a scope defines are declared (unset) on entry; reading or assigning them before their `def` runs fails with `Name used before definition`. Blocks that define nothing get no namespace. Top-level `def`s of class, object, interface and static bodies declare *members*, which bind no unqualified name (reading an uninitialized body member fails with `Member used before definition`).
- **Object model** (`docs/design/bip002_object-model.md`): `class (params) implements I ( body ) static ( … )`, `value class`, `interface extends … ( … )`, `object implements … ( … )`, `this`, `super.m()`/`super(I).m()`, `x is T`, `private`, and the natives `same`/`classof`. Members are reached only as `this.x` or `obj.x`; `this.x` goes through `Members.selectOwn`/`assignOwn`, the only path that may see private members.
  - *Operator methods*: when the left operand of `+ - * /`, or the operand of unary `-`, is a `BabbleInstance`, the operator calls its public `plus`/`minus`/`times`/`div`/`neg` (`Operators.method`, `Operators.NEGATE`; missing: `No such member : plus`). The interpreter does it in `visitBinaryOp`/`visitNegate` (`operatorCall`); compiled code evaluates both operands into locals, then branches on `instanceof BabbleInstance` to the same select and call `invokedynamic` sites `a.plus(b)` compiles to (`operatorCall`) when non-numeric, or lowers directly to JVM primitive instructions when statically numeric (`RM001`). Both use `Interpreter.operatorSite` for the call's messages. The type checker types it as that call when the left type is an `Instance`.
  - *Compound assignment* (`x op= v`, the `op` token of `# assignExpression`, `Operators.compound`) is `x = x op v` with the target read before `v` and an `obj.x` receiver evaluated once: the interpreter's `compound`, the compiler's `compoundAssignment` (sharing `arithmetic` with `visitBinaryOp`), and the type checker's `compoundAssignment` (sharing `binaryOp`); the left operand's text in messages is `Interpreter.targetText` (`x`, `obj.x`).
  - Runtime: `BabbleClass` (callable class value, statics, inherited defaults, `capturedFor` interface cells), `BabbleInstance` (member array, `isMemberDefined(int)` for unboxed fields, `javaDefaultLookup()` for direct Java `default` methods, `face()` returning `this` on compiled classes, value-class equality/hash/`toString`), `BabbleInterface`, `ClassShape` (static description, string-encoded for compiled code), `Classes` (helpers both backends call), `Supers`. Java boundary: `Values.toJava`/`fromJava`/`unwrap`, `Faces` (`Proxy` faces for interpreted instances implementing Java interfaces, and cached `LambdaMetafactory` factories for `0..16`-arg accessible functional interfaces with `Proxy` fallback for inaccessible/higher-arity SAMs), `Overloads`/`JavaTypes`.
- **Runtime boundary** (`docs/design/bip006_module-sources-and-aot.md` §3): what a compiled program needs to run is `org.babblelang.runtime` and the built-ins of `engine.impl.natives` and `engine.impl.natives.java`.
  - `BabbleException` is in `runtime` too, so error messages start with `org.babblelang.runtime.BabbleException:`. The boundary references nothing of the front end (parser, analysis, compiler, interpreter, engine), no third-party library and no JDK module but `java.base`; `RuntimeBoundaryTestCase` enforces it by reading the class files' constant pools. `mvn package` also builds it alone as `babble-<version>-runtime.jar` (classifier `runtime`).
  - `import` reaches modules through the runtime interface `Modules` (`load(name, importerSourceName, rt)`), which the engine implements; `ScriptRuntime` is `(root, writer, modules)`, with no `javax.script`.
  - *babblec* (M5b): `compiler.Babblec.compile(main, root, jar, context)` compiles through `BabbleScriptEngine.compileProgram(source, mainName)` (a `FileModuleSource.rooted(root)`, compile mode; the main module and every module its analysis read, as `ProgramModule`s) and writes a reproducible jar (sorted entries, fixed time stamps): the generated classes, the index `babble/modules.index` (`runtime.ProgramIndex`: main key, the root relative to the jar's directory; per module key, display name, class, exports), the runtime classes copied from wherever `Launcher` was loaded, and `Main-Class: org.babblelang.runtime.Launcher`.
  - The launcher runs the main class's `run(ScriptRuntime, Namespace)` with `args` bound and a `Modules` over the index, resolving import names from the importer's key with `runtime.LogicalPaths`; a module not in the index goes to a `runtime.ModuleCompiler` found through `ServiceLoader` (M5c: the full jar registers `compiler.FileModuleCompiler` in `src/main/resources/META-INF/services`, an engine per root compiling through `compileProgram`; the program's own modules stay the jar's at runtime), and without one fails with `a compiled program only has the modules it imports statically`.
- **Runtime** (`org.babblelang.runtime`, no ANTLR dependency): everything both backends call — `Operators`, `Truth`, `Members`, `Arguments` (the one implementation of argument binding), `Calls`, the `Callable` calling convention `call(ScriptRuntime, Object[] args, String[] names, CallSite)`, `BabbleFunction`/`BoundMethod`, `CompiledFunction`/`FunctionBody`, `IntCell`/`DoubleCell`/`BoolCell`, `CallSite`/`OpSite` (source texts for error messages), `ScriptRuntime` (per-eval root namespace, output writer, `Modules`), and the scopes `Namespace`/`Scope`/`Slot`.
- **Interpreter** (`org.babblelang.engine.impl.Interpreter`): extends the generated `BabbleBaseVisitor<Object>`; one `visitX` method per grammar alternative. It tracks the `last` visited context so `BabbleCompiledScript` can report the line number on error. `return` is a `ReturnException` caught by `Function.invoke`. Class constructors are `InterpretedClassBody`.
- **Compiler** (`org.babblelang.compiler`, `docs/design/bip001_bytecode-compiler.md`): `CodeGenerator` emits a script class (a module's is named after its key, `BabbleCompiler.className`: `lib/vec3.ba` → `babble/lib/vec3$ba`, the same every compilation; other scripts get `org/babblelang/generated/Script$N`).
  - Its methods: `run(ScriptRuntime, Namespace)` (split into `run$k` when large); per function literal, a direct entry point `fn$N$name` (`(self, thiz, rt, binder, Object p0, …)`), an optional `$spec` primitive-signature entry point (`fn$N$name$spec`) when any parameter or return is unboxed (`int`/`double`/`bool`), plus an `fn$N$name$call` array adapter (wrapped as `FunctionBody` via `LambdaMetafactory`; functions with more than 200 parameters only have the array form); one `cls$N$Name` constructor per class/object expression (wrapped as `ClassBody`); real JVM `interface` classes (`InterfaceGen`, `Script$N$iface$k$Name` / `babble/<module>$iface$k$Name`) with `bm$<name>` / `bm$<name>$spec` and JVM `default` methods (`RM003`); and static constant fields built in `<clinit>` helpers.
  - Phase 2 & `RM003`: function, block, class-body and static-block variables are JVM locals, or `Cell`s / `IntCell` / `DoubleCell` / `BoolCell` when captured (function, class, and interface values carry their captured cells); the file, packages, and any scope declaring a `package` keep phase 1 namespaces. Each class/object expression whose body keeps no namespace gets its own JVM class `Script$N$k$Name extends BabbleInstance` directly implementing its Babble JVM interfaces (`bm$<name>` / `bm$<name>$spec` bridges + `$iface$<Id>`) and accessible Java interfaces (exact-signature Java overload bridges + `javaDefaultLookup()`, so `face()` returns `this` without `Proxy` allocation), with a field per member — unboxed `int`/`double`/`boolean` for non-nullable primitive members, with an `int $defined` bitmask and `isMemberDefined` when any unboxed body `def` may be read before init — methods as instance methods + optional `$spec` behind shared `CompiledMethod`s, and hidden `$v$x` fields for constructor cells methods capture; `this.x`/`this.m()` compile to `GETFIELD`/`PUTFIELD`/`INVOKEVIRTUAL` (of `$spec` when typed and positional, else direct entry point).
  - Phase 3, `RM001` & `RM003`: other calls and `obj.x` selections are `invokedynamic` sites bootstrapped by `runtime.Bootstrap` (including typed primitive call sites `(Callable, ScriptRuntime, CallSite, <prim...>)<prim>` resolving to `spec` handles, and `SelectCache` inspecting primitive/reference fields via `MethodHandles.privateLookupIn` across class loaders), with an inline cache of up to 4 guarded fast paths before going generic. Where `TypeChecker` resolves a target statically, `RM001`/`RM003` emit direct Babble `INVOKEINTERFACE` (`bm$<name>$spec`/`bm$<name>`), `INSTANCEOF` for `is`, `INVOKESPECIAL` for `super(I).m()` (with `$super$k` lambda-hoisting helpers), Java `INVOKEVIRTUAL`/`INVOKESTATIC`/`INVOKEINTERFACE`, `NEW`, `ARRAYLENGTH`, field `GET*`/`PUT*` (with `Values.unwrap`, `JavaTypes.wrapInvocationException`, and `Types.check` parity), and indexed `Module.exportAt(index)` reads without `invokedynamic` or `JavaLinker` overhead. Java overload resolution is cached per argument kinds (`Overloads.Cache`, both modes), and its candidates (`JavaTypes.methods`) skip bridge methods except visibility bridges (`StringBuilder.length()`).
  - Invariants: non-`RM001` expressions leave `Object` (`RM001` leaves `I`/`D`/`Z` for unboxed primitives and adapts at boundaries via `emitAs`), and the operand stack is empty at loop heads (HotSpot OSR). `return` emits `IRETURN`/`DRETURN`/`ARETURN` matching the enclosing method/spec descriptor; classes load lazily through per-compile `ScriptClassLoader`s chained across static module imports (`CompositeClassLoader`) and REPL session inputs, with an in-memory hierarchy table backing `ClassWriter.getCommonSuperClass`. Error lines come from the innermost stack frame of the script's classes with a line number.
- **Scoping** (`runtime` package): `Scope<T>` interface with `Slot` holders (`set` initialises, `assign` requires the slot to be set); `Namespace` is the main implementation (`child`, `enterPackage`, `declare`, `initialize`, `assign`, `lookup`). Packages are namespaces; objects are not (they are `BabbleInstance`s). A package changes only through its own code (`n = v` in its body or its functions): `p.n = v` from outside fails with `Cannot assign to a package member : n`, from `Members.assign` at runtime (which tries a `Namespace` before Java targets, since `isJavaObject` would take it for one) and from `TypeChecker.assignedMemberType` when the package is known statically.
- **Natives**: built-ins implement `runtime.Callable`.
  - Native functions live in `impl.natives`: `print` writes to the `ScriptContext` writer, or `to:` any `Appendable`; `same`; `classof`; `ConvertFunction`, the nine conversions `byte(x)`..`string(x)` (integral ones truncating towards zero and failing out of range, all parsing strings), typed by `OperatorTypes.conversion` and reached by both backends through `ConvertFunction.of(name)`.
  - Java interop lives in `impl.natives.java`: `JavaPackage` → `JavaClass` (a `JavaType`, equal by `Class`; members are public member classes, methods, then public fields: static final ones cached as constants, others read on each selection and never cached by `Bootstrap`, `isConstant`; instance fields only through an instance, `value(receiver, name)`; `assign` writes a public non-final field, `Members.assign` sending Java targets there, and refuses a Babble function for a functional-interface field, which needs `Runnable(f)` since member assignment has no `ScriptRuntime`) → `JavaMethod`/`BoundJavaMethod`/`JavaObject` (a `JavaValue` wrapper for objects Babble constructs, printing as its value).
  - Java calls return objects unwrapped; `Members.select` gives any Java object other than Babble's own values (null, numbers, `Boolean`, `Character`, callables; a `String` has its methods, `BIP011-P2b`, typed by `MemberTypes` as `java.lang.String`'s and called with a direct `INVOKEVIRTUAL`) its members through `JavaObject.member`, and `Overloads.resolveMethod` calls a method of an inaccessible class (`List.of()`'s) through the accessible type it comes from (`JavaTypes.accessible`). The type checker types a Java result or static field as `JavaInstance` of its accessible class (`any` for `Object` or when no accessible type exists), and arrays as `JavaArray`. Calling a functional interface's class with one Babble function converts it explicitly.
- **Formatter** (`org.babblelang.format.Formatter`, command line `-format`, `org.babblelang.Babblefmt`): works on the token stream, comments included (the lexer puts them on the hidden channel, so the parser never sees them; anything counting tokens must look at the channel, as `BabbleSession.classify` does).
  - It reads in the parse tree (`BabbleScriptEngine.parseSource`) what each token is: a call's `(` or a block's, a newline that separates expressions (`sep`), continues one (+1 indent), sits in a parenthesised list, or precedes a block/`else`/`static` (dropped unless a comment is in the way). It keeps the source's line breaks otherwise; indentation comes from a stack of open parentheses, each anchored to the line where its `if`/function/class starts.
  - The result is parsed again and must give the same tree, newlines and semicolons aside (`IllegalStateException` otherwise). Note that `;;( … ;;)` closed on its line and followed by code lexes as a line comment (longest match).

## Known issues

- Reading a package member at runtime walks out of the package: `def x = 1 ; package p ( … ) ; p.x` evaluates to `1` (`Members.select` uses `Namespace.get`, which searches enclosing scopes), while the type checker rejects it with `No such member : x`.
- The interpreter cannot run a script's functions on several threads (it keeps the current scope in a field): the fable ray tracer, which renders on 16 threads, only runs in compiled mode.

## Tests

Tests live in `src/test/java/org/babblelang/tests`. Most extend `BabbleTestBase`, which offers `interpret(String)` for inline snippets and `interpretFile(String path)` for `.ba` scripts. End-to-end language tests are `.ba` files in `src/test/babble/` (referenced by relative path, so tests must run from the repo root, as Maven does). In-language `assert(...)` calls are the assertion mechanism inside `.ba` scripts.

- Both modes: `DifferentialTestCase` runs every `.ba` file and a list of snippets in both modes and compares results, output and errors; `BatestTestCase` (`org.babblelang.tests.batest`) runs every `.batest` file under `src/test/batest/` (`{{{{{`/`}}}}}` cases, `==========` virtual modules, `----------` session inputs) with leak-free error normalization (`BIP009`), backed by `-Pbatest` dual-JVM JaCoCo reporting (`BatestCoverageReporter`).
- Modules: `BabbleModulesTestCase` covers modules, in a `MapModuleSource`; `FileModulesTestCase` what is particular to files (real paths, symbolic links, absolute paths), rooted file sources and class path modules; `ModuleSourcesTestCase` the `ModuleSource` contract (an in-memory source that records what it is asked); and `src/test/babble/Modules.ba` with the fixtures in `src/test/babble/modules/`.
- Object model: `BabbleObjectModelTestCase` and `BabbleJavaObjectsTestCase` (§10 of its design doc).
- Compiler and analysis: `BabbleCompilerTestCase` covers compiled-mode specifics (method names, generated classes, stack-trace lines, class verification, method/constant splitting); `ResolverTestCase` has golden tests of name bindings; `TypeCheckerTestCase` has golden tests of type diagnostics (`line:column message`) and checks every `.ba` script checks cleanly; `EffectsTestCase` and `src/test/babble/Effects.ba` cover `RM002` (`BIP007-P1`) effect/algebraic inference, `mut`/`borrow` alias & exclusivity rules, higher-order specialization, and Java `axiom`/`@Pure` boundaries; `RuntimeBoundaryTestCase` keeps the runtime free of the front end.
- Sessions: `ReplTestCase` covers sessions (shadowing, static checks and types across inputs, modules loaded once per session), `classify`, and the loop's transcripts.
- Formatter: `FormatterTestCase` has golden tests of the formatter and checks every `.ba` script of the repository formats to a fixed point; `org.babblelang.BabblefmtTestCase` covers its command line.
- Examples: `ExamplesTestCase` compiles every script of `examples/` without running it (the ray tracers take minutes to run): with `compileProgram` and its static imports in the compiled run, through `compile()` (parse, analysis, type checking) in the interpreted one.
- Command line and babblec: `org.babblelang.MainTestCase` covers the command line (scripts, arguments, `-keep-alive`, `-compile`, exit statuses); `BabblecTestCase` compiles programs into jars and runs them in fresh JVMs with the jar alone (output, arguments, errors, dynamic imports, contents, byte-identical rebuilds), and with Babble on the class path (`runWithBabble`: modules compiled while running, the root).
